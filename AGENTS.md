# IFLoom

An interactive fiction engine for any shape of game: a linear novel, a
management game a week at a time, a social sim with a calendar, places and
characters on their own schedules. The core keeps turns, scenes, stats and
entities; plugins add the rest. Games compile to a static folder that opens
from disk. Pre-release; nothing here is a stable API yet.

## Packages

| Package | What |
|---|---|
| `packages/engine` (`@ifloom/engine`) | State, commands, scenes, conditions, effects, saves (the store, the `SaveDriver` interface and the memory driver) and the view, from its main entry; the plugin API (`definePlugin`, `defineCalls`, `renderAction` and the rest) at `@ifloom/engine/plugin`; test helpers at `@ifloom/engine/testing`. Pure TypeScript, no DOM. It also exports the builders a flowing scene is written with (`text`, `say`, `when`, `cases`, `decide`, `choice`, `image`, `minigame`, `panel`, `fold`, `point`, `jump`). |
| `packages/plugin-calendar` (`@ifloom/plugin-calendar`) | The periods of a day, the days of a week, sleep and a curfew, and what a turn is: a period, a day or a week. |
| `packages/plugin-places` (`@ifloom/plugin-places`) | Locations with exits and things to do, travel between them, and where the player is. A location is an entity carrying the `places/location` trait, written in content's `entities` with `places.location({ ... })` (named by `places.locationRef('park')`), its name, `description` and `image` the entity's. Places are unique, so things lie in rooms: the view lists them with a pick-up button, and `places/holder` names where a dropped thing goes. |
| `packages/plugin-cast` (`@ifloom/plugin-cast`) | Characters with schedules, who is in the room, talking and calling. A character is an entity carrying the `cast/person` trait, written in content's `entities` with `cast.person({ ... })` (named by `cast.character('ava')`), so relationships are stats the game declares on the kind `character`. |
| `packages/plugin-quests` (`@ifloom/plugin-quests`) | Quests: stages done by conditions, progress that is never taken back, tracking and news. |
| `packages/plugin-statuses` (`@ifloom/plugin-statuses`) | Timed statuses that last some turns: stat modifiers read through the engine's `statModifiers`, never written, and effects as one starts, each turn and as it ends. Statuses are content: `data.statuses.statuses`. |
| `packages/plugin-achievements` (`@ifloom/plugin-achievements`) | Achievements earned by a condition after each command or by an effect, secret ones, progress counts, and a record in the profile through its `profile` provider. Achievements are content: `data.achievements.achievements`. |
| `packages/plugin-inventory` (`@ifloom/plugin-inventory`) | Using, dropping and giving away what you hold: the `inventory/usable` trait (`inventory.usable(label, effects)`) and the `use`, `drop` and `give` commands; a dropped thing goes to the holder places names (`places/holder`), else it's gone. Keeps no state; `data.inventory.kinds` filters its view. |
| `packages/plugin-shop` (`@ifloom/plugin-shop`) | Vendors that sell entities for spendable stats: a vendor is an entity carrying the `shop/vendor` trait, written in `entities` with `shop.vendor({ ... })`, that holds a good's stock (none means it never runs out), restocking, selling back and seeded daily discounts, prices from the good or the `shop/sellable` trait; opening hours with the calendar, a place with places. |
| `packages/plugin-jobs` (`@ifloom/plugin-jobs`) | Jobs: hiring requirements, shifts that cost stats and time and pay a wage, promotion ladders, missed shifts and firing; shift days and hours with the calendar, a workplace with places. Jobs are content: `data.jobs.jobs`. |
| `packages/plugin-generators` (`@ifloom/plugin-generators`) | Named pools of values and templates that make entities through `create` (with its `like`, `at`, `tags`, `traits`, `description` and `image`), each drawn field from a pool, a range or a fixed value, seeded and replay-exact. Pools and templates are content: `data.generators`. |
| `packages/plugin-wardrobe` (`@ifloom/plugin-wardrobe`) | Slots, things with the `wardrobe/wearable` trait that go in them, and what each body has on (the player's and each protagonist's), by entity reference; only what you hold is worn. Slots are content: `data.wardrobe.slots`. |
| `packages/plugin-messages` (`@ifloom/plugin-messages`) | Channels and threads of messages that arrive when the story allows; replies are choices. Channels and messages are content: `data.messages`. |
| `packages/plugin-feed` (`@ifloom/plugin-feed`) | Feeds of posts that appear when the story allows, the player's own posts, likes and comments. Feeds and posts are content: `data.feed`. |
| `packages/plugin-devices` (`@ifloom/plugin-devices`) | Devices with apps built from sections; opening one is free and doesn't leave the room. Devices and apps are content: `data.devices`. A phone is this plugin, messages and feed put together by the game's own content (the how-to `how-to/build-a-phone.md`, the showcase's `world/phone.ts`); there's no package for it. |
| `packages/plugin-cheats` (`@ifloom/plugin-cheats`) | Cheats for the player: effects that run in any scene and through any lock, free or refused by `blocked` until a condition holds (a supporter unlock, say), with a log of each use. Unlike debug, it ships in the release. Cheats are content: `data.cheats.cheats`. |
| `packages/plugin-unlocks` (`@ifloom/plugin-unlocks`) | Codes the player enters (a supporter's, say), checked against a slow hash so no code ships; remembered in the profile and recorded in the save for `unlocks/has`. Packs in a game's `src/unlocks/<unlock>.ts` are encrypted into the page by the CLI under the code. Unlocks are content: `data.unlocks.unlocks`. |
| `packages/plugin-debug` (`@ifloom/plugin-debug`) | Debug commands that ignore locks; left out of release builds. |
| `packages/audio` (`@ifloom/audio`) | The audio player: `startAudio(runner)` plays `view.audio` in the browser with plain `HTMLAudioElement`s. Imports only the engine; any UI can use it. |
| `packages/browser` (`@ifloom/browser`) | Browser helpers in plain DOM for any UI: a runner with saves, a profile and an autosave in `localStorage` (`browserRunner`), the save drivers for `localStorage` and IndexedDB (`localStorageDriver`, `indexedDbDriver`), the clock that ticks timers and minigames (`startClock`), keyboard shortcuts (`startKeys`, `startMinigameKeys`), the number for a new save slot (`nextSlot`) and a key that shows held-back prose (`startRevealSkip`). Imports only the engine; the React UI and the templates use it. |
| `packages/react` (`@ifloom/react`) | The React UI: React and shadcn/ui (Radix, Tailwind v4), and `mountGame`. Two entries: `@ifloom/react` (mounting, the layout, every component and hook, customising, `checkUiHints`) and `@ifloom/react/kit` (what components of your own are built from: `PluginUi`, `pluginKit`, `usePlugin`, `useKitPart`, `overridable`, `PartDialog`, the shadcn/ui primitives). Declares its own presentation hints (`ui.transition`, `ui.reveal`, `ui.dice`, `ui.timer`, `ui.tilt`, `ui.display`, `ui.hue`, each once as a `UiHint` in `src/hints.ts`, beside the type it augments), its inline pieces (`modal`, `image`, `mail`, `prop` and `mono`, by augmenting `InlineUi`, each once as an `InlinePiece` in `src/game/inline.tsx`; a game adds its own with `inline`) and `checkUiHints`, built from those declarations over the engine's `uiInContent`. Names no plugin: each plugin's React UI is in that plugin's `/react` subpath, built only from this package's two public entries (`useGame`, words, `ChoiceButton`, `Section`, `usePart` from the main one; `pluginKit`, `usePlugin`, `useKitPart`, `PartDialog`, the button and badge variants from the kit), and a game lists the ones it wants in `plugins` (`PluginUi`, placed by `<Plugins at>`). Presets style the UI's parts, the kit's parts (`data-kit`) and the tokens, never a plugin's parts. One UI among possible others: nothing else depends on it. |
| `packages/cli` (`@ifloom/cli`) | `ifloom new`, `dev`, `build`, `check`, `playtest`, `snapshot`, `words`, the game module's `@ifloom/cli/game` (`defineGame` and `probe`, importing only the engine, so the page imports it too), and the Vite preset `@ifloom/cli/vite`, which knows no UI framework (one HTML file, relative paths). Brings Vite as a dependency; a game lists its framework's Vite plugins itself. Templates `react`, `vanilla`, `vue` and `svelte` in `templates/`, each with its own `vite.config.ts`. Also `next`, a Next.js app that builds with Next and keeps `check` and `playtest` on the CLI, and `plugin`, a plugin package of its own with a test. `ifloom new` also copies the examples. |
| `packages/create-ifloom` (`create-ifloom`) | `npm create ifloom`: the CLI's `newGame` bundled into one `dist/bin.js` with copies of the templates and examples beside it, so it installs nothing else. Same `--template` and `--theme` as `ifloom new`; makes the game in `./<name>` and prints the next steps for the package manager in `npm_config_user_agent`. |
| `packages/ifloom` (`ifloom`) | `npx ifloom`: one `bin.js` that runs `@ifloom/cli`'s bin, so the command runs without installing anything first. Nothing to build. (The checkout's root package is `ifloom-monorepo`.) |
| `examples/showcase` | Small Town: the game that uses every feature. Its tests play it; the docs point at its source. |
| `examples/novel` | The Letter: a linear novel with no plugins, places or clock, the smallest shape of game. |
| `games/` | Not in git: users' own games, made by `npm run new -- <name>`, as workspaces of the checkout. |
| `examples/cafe` | The Corner Café: a management game a week at a time, with staff and dishes as entities. |

Every game, template and example lays out its source the same way: `src/game.ts` only assembles: its default export is the game module, `defineGame({ build, start?, probes?, policy? })`, whose `build({ unlocked })` returns `loadGame(content, base, { packs })` with the plugins and rules, and which the page and the CLI both build the game from; probes are made with `probe`, by playing, never by writing state, `src/rules.ts` holds the game's own code, its `rules` (a `GameRules`), which content calls as `game/<name>`, `src/world/` holds what the whole game shares as one `Content` file per kind (`stats.ts`, `things.ts`, `cast.ts`, ...), and `src/story/` one per area, a place, chapter or arc (`story/cafe.ts`), with its scenes and their words, written in place, and its slice of plugin content; lines read by key go in its `prose` (or a sibling `<area>.prose.ts`). Keep new example content in that layout; the docs page is `how-to/organise-your-files.md`, and `loadGame` reports a key the content declares twice. Packs (mods, `src/unlocks/` content) go in `packs`, over the content.

A first-party plugin is a package of its own that imports only `@ifloom/engine` and `@ifloom/engine/plugin` and requires no other plugin (`packages/engine/tests/contracts/plugin-packages.test.ts` finds every `packages/plugin-*` by glob and holds each to that, to its React UI's imports and to its docs page; `plugin-shape` and `naming` read the same list). One with something for the player also ships its React UI in `src/react/`, the `/react` subpath (`@ifloom/plugin-shop/react`): a `<id>Ui` module (`shopUi`), its components and its hooks, declared once with `pluginKit(id, words)` and read in each component with `usePlugin`, which gives the plugin's view typed by `ViewRegistry`, its words and a `send` for its helpers' commands, importing only the engine, React, `@ifloom/react` and `@ifloom/react/kit` (never a deep path) and its own files, with React and `@ifloom/react` as optional peers. It uses only classes `@ifloom/react`'s own source uses, so no plugin needs a stylesheet (`packages/react/tests/contracts/presets.test.ts`), and marks its parts with the kit's, which bring their own look (`useKitPart('card', 'good')`, adding only layout from `KIT_LAYOUT`). Its main entry declares each condition, effect and command once, with what it takes (`defineCalls`, arguments from `arg`), and each list of its `data` once, with its noun and words (`defineData`): its functions are handed their arguments typed and read from untrusted content, its helpers write calls with the declaration's writers (`CALLS.conditions.at({ ... })`, never a key built from its id), the content checker reports what a call leaves out, gets wrong or names that the game lacks, and its registries extend `ConditionsOf<typeof CALLS>` and the rest (`declare module '@ifloom/engine'`, beside its queries' answers, its view and its traits), so a game that imports it has its calls checked against the same declaration. `references.calls` is only for a rule a declaration can't say. The answers of the queries other plugins ask (`places/here`, `calendar/now`, `cast/contacts`, ...) are declared once in the engine's `PartnerQueries` (`packages/engine/src/partners.ts`) instead, as types only, so a partner reads them typed without importing the plugin. Nothing there runs: the answer is the owning plugin's query, and the fallback without it the asker's. Every player action a plugin's view offers is a ready `RenderedChoice` (built with `renderAction`, refused in advance, worded by the plugin's strings), and a price in it has its `text`, so a UI of any framework draws them as it draws any button and never builds a plugin's command or words. Our UI is never mandatory: a game may draw any plugin itself. It may work with others when the game has them, by name only: it lists them in `cooperates` and asks them through conditions, effects and `query`. It is documented under `docs/content/docs/(latest)/reference/plugins/`, and that suite fails on any export the page does not name. Its tests use `@ifloom/engine/testing` (`loadChecked`, `freshState`, `play`, `partnerCases`).

## How packages depend on each other

- **An `@ifloom/*` package another one uses is its peer dependency, never a dependency.** A plugin peers on the engine, `@ifloom/react` on the engine, `@ifloom/audio` and `@ifloom/browser` (and on no plugin), and a plugin's `/react` subpath on `@ifloom/react`, `react` and `react-dom` as optional peers, with `@ifloom/react` a dev dependency for the workspace. So a game has one copy of each, at the version it chose. npm 7 and later installs a required peer the game doesn't list.
- **Every reference to an `@ifloom/*` package is `^` and its version**, `^0.0.0` for now: in peers and dev dependencies, the examples, the templates and the docs' snippets. A caret on `0.0.x` matches that version only, on `0.x` the same minor, and from 1.0 the same major, so it accepts what semver calls compatible. A release bumps the versions and the ranges together.
- **Other libraries:** what a package runs on its own (Radix, `clsx`) is a dependency. What the game's build or typecheck must share with it is a peer: `react`, `react-dom`, `tailwindcss` and React's types for `@ifloom/react`, whose `.d.ts` files a game's typecheck reads. A game lists its framework's Vite plugins itself.
- Two packages use another without peering on it, since each has to run on its own: `create-ifloom` has `@ifloom/cli` as a dev dependency it bundles at build time, and `ifloom` has `@ifloom/cli` as its one dependency, whose bin it runs. There are no others.
- `packages/cli/tests/contracts/packages.test.ts` holds the first two rules, the two exceptions, and the packaging below.

## Packaging

Every package builds with tsdown to `dist/` (ESM `.js`, `.d.ts`, declaration and source maps), and nothing in the checkout reads it. The `ifloom` package is the exception: it is one `bin.js` and builds nothing.

- **Published.** Every package is public on npm (the `ifloom` org owns the `@ifloom` scope): no `private`, `publishConfig` `{ access: 'public', provenance: true }`, `repository` with its own folder as `directory`, `homepage` (its page on ifloom.dev), `bugs`, `keywords`, the CLI's `engines.node`, a short `README.md` (what it is, how to install it, links to its docs and API page) and a copy of the root `LICENSE`. `npm pack --dry-run -w <dir>` lists what a tarball holds.

- **Exports.** Each entry is `{ "ifloom-source": "./src/x.ts", "types": "./dist/x.d.ts", "import": "./dist/x.js", "default": "./dist/x.js" }`, and `files` is `["dist", "src"]`. A package has `"build": "tsdown"` and a `tsdown.config.ts` that calls `define([...entries])` from `tsdown.base.ts`. `@ifloom/react`'s build also writes `styles.min.css` and `themes/<preset>.min.css` with the Tailwind CLI. The CLI's `bin` is `bin.js`, which imports `#bin`: `src/bin.ts` under the condition, `dist/bin.js` otherwise. create-ifloom's `bin` works the same way, and it has no `exports`.
- **The source condition.** The checkout's tools resolve `ifloom-source`, so they run `src/` with no build: Vitest (`vitest.config.ts`), tsc (`customConditions` in `tsconfig.base.json`), the Vite preset for a game inside the checkout (`packages/cli/src/source.ts`, which also loads its `vite.config.ts` natively), and Node through `.npmrc`'s `node-options` (so `npx ifloom` runs the CLI's source too, which needs Node 22.18 or later to strip the types). A test that starts Vite on a fixture passes `configLoader: 'native'`. Anything outside the checkout gets `dist/`. So a change to a package shows up straight away in the examples and in `games/*`, except a `next` game: Next has no setting for the condition, so run `npm run build` before its `dev` or `build`, and again after changing a package.
- **Building.** `npm run build` builds every package, each after the @ifloom packages it uses; `npm run pack` also packs each into `packs/` for a game beside the checkout (`scripts/pack.ts`). `scripts/try-dist.sh` builds, imports every export from `dist/` in plain Node and type-checks a consumer against the `.d.ts` files; run it when a package's entries, exports or build change.

`packages/engine/tests/fixtures/` holds a small town game with no story; engine tests run against it. The showcase is `examples/showcase`.

## Rules the engine keeps

- **Deterministic.** Every draw goes through `random.ts`, hashed from the save's seed, the turn and a name. Same save, same cards.
- **Nothing loads at runtime.** Everything a game needs is bundled when it is built, because a game opened from disk can fetch nothing. `tests/contracts/boundary.test.ts` enforces it.
- **No genre, no game.** The engine knows no stat, phase, place or person by name; a game declares them and supplies its own logic through `pack.rules`. Examples, comments and docs use everyday, neutral fiction.
- **Standalone.** The engine imports nothing outside its own folder.
- **One naming rule for content**. A condition's or effect's target is named by its noun (`stat`, `entity`, `storyline`, `scene`; `key` in a kv store), `by` changes a number and `to` sets a value, and a command names its one target `id`. Plugin kinds follow it too. `tests/contracts/naming.test.ts` holds every kind to it.
- **One plugin shape**. A hook runs at an event and returns the next state, named `onX` (`onTurn`, `onTurnDone`, `onStat`, `onCommand`, a plugin's or the game's `rules`); a provider answers and changes nothing, named by its noun (`guard`, `label`, `view`, `profile`); nothing is nested. A plugin call's short form takes its arguments as an object, `{ 'places/at': { location } }`, and every helper writes it. A plugin's helpers are properties of its factory, named after the call they write (`places.at('cafe')`, `quests.done('bread')`, `calendar.sleep()`), with its definers too (`places.location({ ... })`, `cast.person({ ... })`), put there with `Object.assign(placesPlugin, { ... })`; a plugin exports no bare helper. Values take arguments. Anything a mod could change is content in pack `data`, never a plugin option. `tests/contracts/plugin-shape.test.ts` holds the first-party plugins to it.
- **One separator rule for ids**. An id is letters, digits, `-` and `_`, in parts joined by `.` (`cafe.counter`, `place.cafe.ava`); `/` names a plugin (`quests/done`, `calendar/period.morning`); `#` is a choice in a scene or a reply (`ch1.mat#open`, in labels, `chose` and `state.chosen`); `:` is a reference with what it is in front (`character:ava`, `mod:naps`, the profile's `core:settings` and `ui:gate`). `tests/contracts/ids.test.ts` holds the examples, the templates and the showcase's plugin content to it.
- **Presentation lives in UI packages.** The engine owns what changes the state, the rules or a replay, and content every UI must read the same way (a scene's words, a stat's value, an entity's picture). How things look and move is a UI's: content writes it as `ui` hints, which the engine carries to the view as written and checks only for being data. A UI package declares its hints by augmenting `SceneUi`, `ChoiceUi`, `BlockUi`, `StatUi`, `EntityUi` and `GameUi`, and checks them itself. Prose does the same with UI pieces, `[[ui:name|words|arg]]`: the view carries each as an opaque `ui` span, and a UI declares its names in `InlineUi` and draws them. Don't add a transition, a layout or a colour to the engine.
- **Framework-neutral.** The engine and the plugins' engine side import no UI framework; React lives only in `@ifloom/react` and in each plugin's `src/react/`, which a game drawn another way never loads, and the CLI and its Vite preset name no framework: each game's `vite.config.ts` adds its own framework's plugin (and Tailwind for the React UI). The `vanilla` template proves a game runs without React.

## Words

Author-facing words, used in docs and new API: scene, choice (an option in a scene, a `Choice` in its `choices` or a decision's, which the player chooses and the view hands over as a `RenderedChoice`; never call it an action, though both have `ButtonDef`'s fields, and never a pick, which is random), flow (a scene's body read top to bottom as the player chooses: it waits at a decision, shows the chosen choice's `then`, then carries on after it; the save keeps the visit's path in `state.flow`, and a past choice is a `chose` beat where it was made), decision (a `{ decide, choices }` block, written `decide()`, where the flow waits for the player to choose; never "branch point"), point (a `{ point }` block, written `point()`, a place in the flow a choice can go to, anywhere in the body, a section or a choice's `then` included), jump (a choice's `{ point }` effect, written `jump()`, the only way a flow loops, so it loops only through a choice), fold (a section the player opens and shuts, written `fold()`: presentation only, the React UI's `fold` hint, never state), speech (a spoken line, written under who says it by id: `@ava: "…"` in prose or `say('ava', words)` in a flow, with a bare id read as a scene's `speaker` is, a full reference, `@you` for whoever the player is playing or `@player`; the view shows the name from the entity, or the player's, so prose never writes a speaker's name; `Name: "…"` is only a label with no speaker), action (something the player can do outside a scene's choices, offered by the game, a plugin's entity such as a location or a character, or inline in prose: an `ActionDef` with a `label`, `when`, `blocked`, `cost`, `effects`, a `command` and `once`, the fields a choice has, sent as `{ type: 'action', id }`; one with no label is no button, only done by its command; never "activity", and never call it a choice), button (only the control a UI renders for a choice or an action from its `RenderedChoice`: say "choice" or "action" for what content declares and "button" only for what the player presses), location (an entity with the `places/location` trait, written with `places.location({ ... })`, where the player can be; never "place" or "room" for it, "places" is only the plugin's name, and where the player is now is "here", as the `places/here` query says), room (only what the screen shows while no scene is open, a provider's `RoomScene`, keyed `room:<id>` or `room` in `view.scene`; with places it shows the location the player is at, so "the room" is the screen and "the location" the entity), character, storyline, stage (a step of a quest, and only that), picture (a layered picture with hotspots, on a scene or a location: its `picture`, a `PictureDef` of `layers`, each a file or a pool's pick shown while its `when` holds, and `hotspots` that take a choice or send a command; rendered as `view.scene.picture` or a location's `location.picture` by `pictureView`, and by the React UI's `LayeredPicture`; never "stage"), stat, kv (the kv store: keys with a true/false, number or text value, the player's, or in `of` an entity's, a storyline's (`'storyline:<id>'`) or the running minigame's (`'minigame'`), printed in prose as `{{key}}` or `{{kv:key of=…}}`; the stretch of the game the player is in is the key `phase`, nothing more; never "flags" or "variables", since flags are something else), blocked (why something can be refused: `{ when, reason, hide? }`, refused while `when` holds, its reason words in place or a string by key, `{ string: 'shop/closed' }`, read with `reasonOf`; a vendor's opening hours are one, `shop.hours(...)`; never "requires" or "locked"), effects (each told apart by its key, as a condition is: `{ stat: 'coins', by: -2 }`, `{ scene: null }`; never a `kind` field), cost, once (`once: { per: 'game' | 'turn', reason? }`, the one shape for a choice, an action, a cheat and, as `{ per }`, a trigger), turn, kind (a sort of entity, such as `staff`, `photo` or the cast's `character`, declared in `kinds` with a label, `unique` when each is one particular thing that can hold others, else its things stack, whether it's `listed`, its tags, its `flags`, and default traits; "kind" means only this, so a beat, a span, an input, a setting or a missing file says what it is in `type`), flags (a kind's `flags`: named true/false conditions asked of each listed entity with `'$'` as it, answered in the view as each entity's `flags`, such as `{ met: true }`; the word means only this, never the kv store), entity (what it is lives in content, its name, `description`, `image`, `tags`, traits and starting stats and kv; the save keeps only what play changed, and reads fall back to content; never copy a definition into a save), name, title, label and description (one word each for what a player reads: `name` for a thing, an entity, a status, an achievement, a quest, a cheat, a job or an unlock; `title` for a heading, a scene's, a page's or a minigame's; `label` for a button or a field; `description` for a thing's line; never `desc`, `summary` or `tag`), trait (a named piece of data an entity carries, never functions: written on a kind as a default, on an entity, or in a content or pack `traits` table, row over the entity's own over the kind's, and read with `traitOf(state, game, ref, id)`, which knows one made in play `like` another, or `declaredTrait` from content alone, for a check; an id with a `/` is a plugin's, which declares it in its `traits` and types it by augmenting `interface TraitRegistry`, and one without is the game's), listed (whether the view shows a kind's entities: a kind's `listed`, true, false or a condition with `'$'` as each entity, narrowed by an entity's `visible`; the engine filters, so nothing unlisted reaches the view, and a UI splits what's listed by a kind's `flags` rather than hiding more; a game's kinds are listed by default, a plugin's are not), holder and held (a holder is who has things: `'player'`, a unique entity, or `'you'`; what a holder has is what it holds, and `held` is the save's record of counts play changed, read over each entity's `at` in content; only unique entities hold, other kinds stack, and nothing holds itself), you (`'you'` is whoever the player is playing now: the protagonist the `you` effect chose, else `'player'`; never call it "the current character" or "the active player"), trigger, lock, variants, body (a scene's or a room scene's `body`, its list of blocks; the view gives it back as `beats` to render and as `body`, the same words as markup text), block (one entry of a body as content writes it, a `Block`: `text()`, `say()`, `decide()`, `point()`, or a `{ prose }`, `{ variants }` or `{ media }` block; content has blocks and the view has beats), beat (one piece of a rendered body in the view, a `SceneBeat`, such as a paragraph, a spoken line, a picture or a past choice, for a scene, a message, a post or an app; never a block), words in place (the words a player reads are written in the field that shows them: a `{ text }` block, written `text()`, a `say` line, a `label`, a `name`, a `reason`; never a prose key there, and the checker reports one), prose key (a line kept in content's `prose` table and read by key: a `{ prose }` block, a variants member, a tooltip's or the React UI's modal's line; for a line several scenes share, a set drawn at random, or one a mod rewrites by key), words table (a pack's `words`: other words for the fields a player reads, by key, `<list>.<id>.<field>` (`action.wait.label`, `entity.character:ava.name`, `scene.cafe.counter.choice.tea.label`, `scene.cafe.counter.text.<id or hash>`, `<plugin>/<list>.<id>.<field>`), laid over the merged content by `loadGame` and listed by `translatableFields`; a plugin declares its fields in its data lists' `words` (`defineData`), its calls' word arguments with `arg.words()` and a trait's with `TraitDef.words`; a translation is one pack with it, its `prose` and its `strings`; never call it strings, which are the engine's and plugins' own lines read with `stringOf`), tag, thing (anything a game keeps that the player can hold or collect, such as a sandwich, a note or a photo: an entity, held by a holder; say "thing" for what can be held and "entity" for any entity, a character, a location or a vendor included; never "item", which the engine no longer has (only a note on old saves names it, and an entry of a list is an entry), nor "collection", nor "good"), good (a vendor's entry for a thing it sells, a `GoodDef` in its `goods` with its price and stock; what is sold is a thing), save, mod, render and draw (render is turning a state into what the player sees, as `screen`, `view`, `renderAction` and a UI's components do, and show says what the player then sees; draw and pick mean only a seeded random pick, as `draw`, `drawOne`, a pool, variants, a generator or a vendor's daily discounts make; never "draw" for rendering, though exported names such as `drawChoices` keep it), ui hints (presentation hints: a `ui` field on a scene, choice, block, action, stat, kind, entity, location or the game, carried to the view as written and given meaning only by a UI package, such as the React UI's `transition`, `reveal`, `dice`, `timer`, `display` and `hue`; never engine fields), UI piece (a piece of a UI's own inside a line of prose, `[[ui:name|words|arg|…]]`, such as the React UI's `modal`, `image`, `mail`, `prop` and `mono`: the view carries it as a `ui` span with its name, words and arguments, and only a UI gives it meaning, so it never changes the state; a dialog whose buttons change the game is a panel opened by an inline action instead), roll (a dice roll the `roll` effect makes: seeded from the save, its total kept in the kv store under its key, read with the `roll` condition, and the last command's listed in `view.rolls`; a check is a roll with a target, `against`), timer (a named countdown in real time: declared in content's `timers` with its `ms` and the `effects` that run when it runs out, started, stopped and extended by the `timer` effect, read by the `timer` condition, listed in `view.timers`, and run down only by the logged `tick` command, which also runs a minigame's clock; the save keeps only `{ left, total }` per running timer, and the engine keeps no clock: a UI's, such as `startClock`, sends the ticks), amount (a number content names that is worked out when it's read, an `Amount`: a number, a stat by id or `{ stat, of }`, a kv key's number `{ kv, of }`, a value `{ value, with }`, a count `{ count }`, or a formula of them; read with `amountOf`, taken by range bounds, a `stat` effect's `by` and `to`, a `kv` effect's `by` and `random`, `entity` and `move`'s `by`, a stat's `min` and `max`, a roll's `plus` and `against`, and plugin fields such as an achievement's progress; a plugin's own field that takes one is named to the checker as `{ amount }`; never "value" for it, which is a value by name). Developer words: plugin, the showcase (the example game in `examples/showcase` that uses every feature, called "the showcase" in the docs; "Small Town" is only its title, given once where a page first points at it, and the engine's own test game is "the test fixture"), game module (the default export of a game's `src/game.ts`, a `GameModule` made by `defineGame`; always "game module", since a bare "module" is any JavaScript module), content and pack (content is the game's own, in its files: a `Content` with no id or schema, each key declared once across it, never upgraded; a pack is what comes from outside the code, a mod, unlocked content or a JSON export: a `Pack` with an `id` that saves record, a `schema` that `upgradePack` carries forward, and optional `patches`, laid over the content last-wins; never call the game's own files packs; anything a mod could change is content, never the base `loadGame` takes, which holds only `id`, `title`, `version`, `plugins` and `rules`; a plugin can bring content of its own in `content`, merged first, under the game's), rules (the game's own code, `GameRules`, a plain object with what a plugin has, hooks, providers and the `conditions`, `effects`, `macros`, `values`, `queries` and `commands` content calls as `game/<name>`, `game` being a reserved plugin id; the engine runs it as the first plugin, through the same hooks and providers and with the same context; never "custom"), macro (an effect that stands for other effects, in a plugin's or the game's `macros`: a function that returns the effects it stands for, so prices, guards and locks see them, where an `effects` function returns the next state), hook (a plugin's or the game's `onX`, run at an event, returning the next state), provider (a plugin member that answers a question and changes nothing, named by its noun: `guard`, `price`, `label`, `scene` (what the screen shows while no scene is open, a `RoomScene`, such as the location the player is at), `view`, `profile`), registries (the interfaces a plugin augments to type what content writes for its calls by full name, `ConditionRegistry`, `EffectRegistry`, `CommandRegistry`, the answers of its `QueryRegistry` and its view in `ViewRegistry`, as it types its traits in `TraitRegistry`; a name nobody declares stays loose, and the game declares its `game/…` calls the same way, beside its `rules`), entity reference (`EntityRef`, `` `${string}:${string}` ``, what the engine hands back; the functions that read an entity take any string, as content writes them), options (a plugin factory's settings, code a mod can't change; content goes in `data`), panel (a named piece of UI over the story that the UI renders by name, such as `shop` or `jobs`, shown as `view.panel`: content opens one with the `panel` effect, `{ panel: 'shop', with }`, kept in `state.panel` until `closePanel`, a turn ending or the scene changing, and a scene's `panel: { panel, with }` holds one open for as long as the scene is; a plugin with a panel puts what it shows, filtered by its `with`, in its view's `panel` (the jobs on the open board, the open counter's vendor), found with `panelOf`, so no UI filters; also a game's own UI component, named in `panels`, which can stand for one; the React UI's built-in boxes are cards: `LocationCard`, `DebugCard`), lookup (a function that reads what content declares or play made: `xOf(game, id)` for one definition, such as `sceneOf`, `statOf` or `questOf`, `xsOf(game)` for a list, such as `questsOf`, and `xOf(state, game, ref)` for what an entity is now, such as `personOf` or `locationOf`; every function that reads the game in play takes `(state, game, …)` in that order, with the game required, as `holds(state, game, condition)` does), view, state slice, snapshot (the runner's `RunnerSnapshot`, `runner.snapshot()`: everything a UI renders in one value, the `view`, `settings`, `backlog`, `canUndo` and `canRedo`, `saves` and the helpers' reports, a new object whenever a part changes and handed to each `runner.subscribe` listener, so a UI renders from it rather than asking the runner piece by piece; the scene records `ifloom snapshot` writes are the CLI's, another thing), helper (code started beside a runner that works on it from outside, shaped like `startClock`: one call that returns the way to stop; one with something for the player to see reports it with `runner.setHelper(id, value)` into the snapshot's `helpers`, typed in `HelperRegistry`, as `startUnlocks` reports `helpers.unlocks`), content checker (`checkGame`, the one walk that checks a game's content and lists the files it names), references (what a condition, effect, command or plugin's content names, from each kind's `references` entry and a plugin's `references`), content migrations (`upgradePack` in `upgrade.ts`, the one way a pack written for an older `SCHEMA` comes in: its `PACK_STEPS`, one per schema change keyed by the schema it upgrades from, as `STEPS` in `intake.ts` are for saves, with each plugin's own `contentMigrations` for what that plugin reads, from the version the pack records in `plugins`; the engine's steps know no plugin, and a first-party plugin numbers its `contentVersion` by the engine's schema, so a change to its content bumps `SCHEMA` too; `loadGame`'s `packs` go through it, mods included, since the mod store keeps a pack as written, and content never does; command logs record `schema` and each plugin's `commandVersion`, and `replay` runs `COMMAND_STEPS` and each plugin's `commandMigrations` from there), state intake (`loadState`, the one way a state from outside, such as a save, comes into play: the engine's steps, the plugins' and the game's migrations, then what the game declares; a new game comes from `startingState`, and both read each field's defaults from `FIELDS` in `intake.ts`, which holds the core's fields and each feature's `state`). Result (`Result<T>`, `{ ok: true, value } | { ok: false, reason }`: what the runner, the save and mod stores, `loadState`, `replay` and `upgradePack` answer when something can fail in a way a caller should expect; they never throw for those, and the engine's `apply` gives the same shape with the state on both sides; `checkGame`'s problems are a report, not a failure). Feature (a core feature, such as scenes, stats, entities, holdings or triggers: each one module in `src/features/` that declares its state, kinds, pack key, checks and the references it resolves, view piece, after-command steps, fills and carries; never a plugin), `defineFeature` (how a core feature is declared; internal, not exported). `screen` (`screen(state, game)`, one state rendered once: the open scene or the room, its choices with their effects, availability and price, the scene's picture, the plugins' views, and the pool picks and audio they imply; `view` formats it into what every UI renders, worded and free of spoilers such as a choice's effects, and the reducer records picks and audio from it, so each state is rendered once). Page, in the React UI only: the title screen and the pages around the game (settings, load, credits, the gate and any a game adds), turned on with the `pages` option. Never call those screens, so `screen` keeps one meaning. Layout, story and section, in the React UI only: the layout is the page as a component (`src/layout.tsx`, `DefaultLayout`) made of regions (`Game`, `Sidebar`, `Story`, `Overlay`); the story is the main column (`data-part="story"`), never "stage", which is only a quest's; a section is a titled `Section` of a layout that folds (`collapsible`) or opens in a dialog (`dialog`). The code uses these words too (storyline, character, `View`, `Game`, `Content`, `Pack`, stages, blocks, variants); `docs/content/docs/(latest)/upgrading/status.md` lists the few renames still to come.

Every user-visible change adds a line to `CHANGELOG.md`, under `[Unreleased]` in Added, Changed, Removed or Fixed. Write it for someone making a game, not as a commit message. The docs show it at `/docs/changelog`.

## Adding to the core

A core kind of condition, effect or command, or a field of the state, belongs to a feature in `packages/engine/src/features/`. To add one:

1. Add its type to the feature's shape (`SettingsShape`, say) and its entry to the matching table in the feature's `defineFeature`. The public `Condition`, `Effect`, `Command`, `Reference`, `GameState`, `Game`, `Content`, `Pack` and `View` are built from the shapes, so there's nothing else to edit. A new kind of reference goes in the shape's `references`, by the key that tells it apart, and its resolver in the feature's `resolve`, which the types hold to every kind the shape declares. A pack key goes in the shape's `pack`, merged by the feature's `pack` (built from `mergedById`, `mergedByKey`, `lastWins`, `appended` and `together`), and said in its `content`: what a piece of content declares under it (`byId('timer')`, for the report of one thing declared twice) and the words a translation can give (`listWords('timers', 'timer', { label: true })`, or `null`). Both are typed complete, so a new key can't go unchecked or untranslated, and the loader and the words table read them through the registry.
2. For a new feature, write the module with `defineFeature`, then add it to `FEATURES` and its shape to `Shapes` in `features/registry.ts`. Where it goes in `FEATURES` matters: its after-command steps, checks, fills and words run in that order. Nothing outside the feature and the registry names it.
3. Keep the feature a leaf. Import only types, other features, `strings`, `entities`, `holdings`, `notices`, `storylines`, `range` and `sceneBody`; take everything else (`holds`, `runEffects`, `buildEffects`, `weighted` and the rest) from the `FeatureContext` argument. `tests/contracts/features.test.ts` fails otherwise.
4. A helper the engine exports that needs the core (`statValue`, `lockOn`, `actionOf`) stays in its module outside `features/` (`stats.ts`, `locks.ts`, `action.ts`), which binds the core's context and calls the feature's version.
5. `src/core.ts` keeps only the kinds that are no feature's: `all`, `any`, `not`, the custom calls and `start`.

## Docs

Anything the engine exports is documented in `docs/content/docs/`, published at https://ifloom.dev with the docs under `/docs/`. A change to the exports ships with its docs in the same change. Every ```` ```ts ```` and ```` ```tsx ```` block in the latest docs compiles against the packages, and every `shape` block matches its export (`docs/lib/check-blocks.ts`, run by `docs/snippets/tests/doc-blocks.test.ts`); a block that isn't a program says so with `fragment` in its fence, and one that uses `game`, `state`, `runner` or `view` without making or importing it says `given`. The API section (`docs/content/docs/(latest)/api/`) is generated from the source and its TSDoc by `npm run api-docs`, and `docs/snippets/tests/api-docs.test.ts` fails when it's out of date: a change to an export or its comments commits the regenerated pages too. The pages live here, beside the code, with the snippets they include (`docs/snippets/`, a workspace) and their contract tests; the website that shows them, with the homepage (Next.js with Fumadocs), is its own repo, [IFLoom/ifloom-site](https://github.com/IFLoom/ifloom-site). `npm run docs:dev`, `docs:links` and `docs:build` run `scripts/site.ts`, which runs the site from a checkout beside this one (`../ifloom-site`, or `$IFLOOM_SITE`) against these docs as they are on disk.

The pages are plain Markdown (`.md`) with a `title` and a `description` in front matter, and links between pages are absolute: `[Scenes](/docs/reference/scenes#scene)`. Each folder's `meta.json` gives the sidebar's order, and each top folder is a tab: the Tutorial (`tutorial/`: two tutorials read in order, a short story with no plugins in `tutorial/story/` and a small town with places and time in `tutorial/town/`), How-to guides (`how-to/`: one task each, such as adding a location or shipping the game, with `how-to/render/` for rendering each feature in a UI of your own and `how-to/react/` for the React UI), Explanation (`explanation/`: how IFLoom works and why), the Reference (`reference/`: the engine's exports, one page per feature, with the packages in `reference/plugins/`, `reference/react/`, `reference/browser/` and `reference/cli/`), Upgrading (`upgrading/`: moving to a newer engine, the schema history and old saves), the API (`api/`: every export's signature and fields, generated) and the changelog. A page that moves gets a redirect in `MOVED` in the site repo's `next.config.mjs`, for the page and its Markdown under `/llms.mdx/`. `npm run docs:links` fails on a link to a page or heading that isn't there.

The docs are versioned: `docs/content/docs/(latest)/` holds the latest docs, and each other folder there is a released version, served at `/docs/<version>/`. Don't edit a released version except to fix something that was wrong in it.

## Verify

```bash
npm test             # engine tests, boundary rules, docs coverage
npm run check        # the format and lint (vp check), then npm run typecheck; any lint warning fails
npm run typecheck    # strict: tsc on each package, example and the docs' snippets
npm run format       # rewrites the code in the repo's format (Oxfmt)
npm run docs:build   # the site repo's check against these docs: lint, typecheck, links, next build
```

The checkout's own tools run through [Vite+](https://viteplus.dev) (`vite-plus`, a dev dependency of the root only): the task runner `vp run`, Oxfmt and Oxlint. The root `vite.config.ts` holds their settings and the tasks: `build:<package>`, `typecheck:<project>` and `test:all`, run by `npm run build`, `npm run typecheck` and `npm test`. A task is cached by the files it read, so it runs again only when one of them changes, and a cached build puts `dist/` back. `npx vp run typecheck:plugin-shop` runs one task, and `npx vp cache clean` empties the cache. A fresh clone needs no `npm run build` first, but run `vp` through npm (`npm run`, `npx vp`): it loads every workspace's `vite.config.ts` to list the tasks, and the examples' import `@ifloom/cli/vite`, which without `dist/` resolves only through `.npmrc`'s source condition. A bare `vp`, or a script that spawns it, passes `--conditions=ifloom-source` in `NODE_OPTIONS`, as `scripts/pack.ts` does. With no `dist/`, vp prints an `UNRESOLVED_IMPORT` warning for each example's config; it's harmless. The format is the code only, at 160 columns: Markdown, JSON, CSS, HTML and YAML keep their hand-made shape. Oxlint also runs its type-aware rules (tsgolint, `typeAware` in the `lint` block) over every project but the CLI's templates, and any warning fails the check; the `lint` block says which rules are off and why. The typecheck itself stays on tsc. Nothing a game, a template or a package's user gets depends on Vite+; the CLI builds games with plain Vite.

`scripts/verify.sh` checks what a change can break, by the files it touches (it says which tier it picked and why). A change to docs pages or the changelog alone runs the contract tests that read the docs and the link check, in under a minute; one to the docs' snippets adds their typecheck and tests. Anything else runs `npm test`, `npm run check`, and the examples' check, build and snapshot, all from `src/`, plus the docs build when the docs changed too. `--full` runs everything (CI does), and `--dry-run` says what it would run. `scripts/try-dist.sh` checks the built packages (see Packaging). `scripts/try-templates.sh [--pm npm|pnpm|yarn|bun|all]` packs the packages, makes a game from each of the `react`, `vue`, `svelte`, `vanilla` and `next` templates (and a package from `plugin`) in a temporary folder outside the checkout, installs the tarballs with that package manager, and runs its check, playtest, build and typecheck. With each package manager it also makes one game with create-ifloom's bin from its tarball (`--create <template>`, `react` by default). Run it when a template, the Vite preset, the build, create-ifloom or a package's dependencies change.

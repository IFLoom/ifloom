# IFLoom

An interactive fiction engine for any shape of game: a linear novel, a
management game a week at a time, a social sim with a calendar, places and
characters on their own schedules. The core keeps turns, scenes, stats and
entities; plugins add the rest. Games compile to a static folder that opens
from disk. Pre-release; nothing here is a stable API yet.

## Packages

| Package | What |
|---|---|
| `packages/engine` (`@ifloom/engine`) | State, commands, scenes, conditions, effects, saves, the plugin API. Pure TypeScript, no DOM. |
| `packages/plugin-calendar` (`@ifloom/plugin-calendar`) | The periods of a day, the days of a week, sleep and a curfew, and what a turn is: a period, a day or a week. |
| `packages/plugin-places` (`@ifloom/plugin-places`) | Locations with exits and things to do, travel between them, and where the player is. Each location is a unique `location:<id>` entity, so things lie in rooms: the view lists them with a pick-up button, and `places/holder` names where a dropped thing goes. Locations are content: `data.places.locations`. |
| `packages/plugin-cast` (`@ifloom/plugin-cast`) | Characters with schedules, who is in the room, talking and calling. A character is an entity carrying the `cast/person` trait, written in content's `entities` with `person({ ... })` (named by `character('ava')`), so relationships are stats the game declares on the kind `character`. |
| `packages/plugin-quests` (`@ifloom/plugin-quests`) | Quests: stages done by conditions, progress that is never taken back, tracking and news. |
| `packages/plugin-statuses` (`@ifloom/plugin-statuses`) | Timed statuses that last some turns: stat modifiers read through the engine's `statModifiers`, never written, and effects as one starts, each turn and as it ends. Statuses are content: `data.statuses.statuses`. |
| `packages/plugin-achievements` (`@ifloom/plugin-achievements`) | Achievements earned by a condition after each command or by an effect, secret ones, progress counts, and a record in the profile through its `profile` provider. Achievements are content: `data.achievements.achievements`. |
| `packages/plugin-inventory` (`@ifloom/plugin-inventory`) | Using, dropping and giving away what you hold: the `inventory/usable` trait (`usable(label, effects)`) and the `use`, `drop` and `give` commands; a dropped thing goes to the holder places names (`places/holder`), else it's gone. Keeps no state; `data.inventory.kinds` filters its view. |
| `packages/plugin-shop` (`@ifloom/plugin-shop`) | Vendors that sell entities for spendable stats: each vendor is a unique `vendor:<id>` entity that holds a good's stock (none means it never runs out), restocking, selling back and seeded daily discounts, prices from the good or the `shop/sellable` trait; opening hours with the calendar, a place with places. Vendors are content: `data.shop.vendors`. |
| `packages/plugin-jobs` (`@ifloom/plugin-jobs`) | Jobs: hiring requirements, shifts that cost stats and time and pay a wage, promotion ladders, missed shifts and firing; shift days and hours with the calendar, a workplace with places. Jobs are content: `data.jobs.jobs`. |
| `packages/plugin-generators` (`@ifloom/plugin-generators`) | Named pools of values and templates that make entities through `create` (with its `like`, `at`, `tags`, `traits`, `desc` and `image`), each drawn field from a pool, a range or a fixed value, seeded and replay-exact. Pools and templates are content: `data.generators`. |
| `packages/plugin-wardrobe` (`@ifloom/plugin-wardrobe`) | Slots, things with the `wardrobe/wearable` trait that go in them, and what each body has on (the player's and each protagonist's), by entity reference; only what you hold is worn. Slots are content: `data.wardrobe.slots`. |
| `packages/plugin-messages` (`@ifloom/plugin-messages`) | Channels and threads of messages that arrive when the story allows; replies are choices. Channels and messages are content: `data.messages`. |
| `packages/plugin-feed` (`@ifloom/plugin-feed`) | Feeds of posts that appear when the story allows, the player's own posts, likes and comments. Feeds and posts are content: `data.feed`. |
| `packages/plugin-devices` (`@ifloom/plugin-devices`) | Devices with apps built from sections; opening one is free and doesn't leave the room. Devices and apps are content: `data.devices`. |
| `packages/plugin-cheats` (`@ifloom/plugin-cheats`) | Cheats for the player: effects that run in any scene and through any lock, free or refused by `blocked` until a condition holds (a supporter unlock, say), with a log of each use. Unlike debug, it ships in the release. Cheats are content: `data.cheats.cheats`. |
| `packages/plugin-unlocks` (`@ifloom/plugin-unlocks`) | Codes the player enters (a supporter's, say), checked against a slow hash so no code ships; remembered in the profile and recorded in the save for `unlocks/has`. Packs in a game's `src/unlocks/<unlock>.ts` are encrypted into the page by the CLI under the code. Unlocks are content: `data.unlocks.unlocks`. |
| `packages/phone` (`@ifloom/phone`) | A bundle, not a plugin: `phone()` wires devices, messages and feed into a smartphone, and returns the phone as `data`. |
| `packages/plugin-debug` (`@ifloom/plugin-debug`) | Debug commands that ignore locks; left out of release builds. |
| `packages/audio` (`@ifloom/audio`) | The audio player: `startAudio(runner)` plays `view.audio` in the browser with plain `HTMLAudioElement`s. Imports only the engine; any UI can use it. |
| `packages/browser` (`@ifloom/browser`) | Browser helpers in plain DOM for any UI: the minigame clock (`startClock`), keyboard shortcuts (`startKeys`, `startMinigameKeys`), the number for a new save slot (`nextSlot`) and reveal timing. Imports only the engine; the React UI and the templates use it. |
| `packages/react` (`@ifloom/react`) | The React UI: React and shadcn/ui (Radix, Tailwind v4), and `mountGame`. Reads plugins' views by their exported types, with `import type` only and the plugins as optional peers, so it bundles no plugin. One UI among possible others: nothing else depends on it. |
| `packages/cli` (`@ifloom/cli`) | `ifloom new`, `dev`, `build`, `check`, `playtest`, `snapshot`, and the Vite preset `@ifloom/cli/vite`, which knows no UI framework (one HTML file, relative paths). Brings Vite as a dependency; a game lists its framework's Vite plugins itself. Templates `react`, `vanilla`, `vue` and `svelte` in `templates/`, each with its own `vite.config.ts`. Also `next`, a Next.js app that builds with Next and keeps `check` and `playtest` on the CLI, and `plugin`, a plugin package of its own with a test. `ifloom new` also copies the examples. |
| `packages/create-ifloom` (`create-ifloom`) | `npm create ifloom`: the CLI's `newGame` bundled into one `dist/bin.js` with copies of the templates and examples beside it, so it installs nothing else. Same `--template` and `--theme` as `ifloom new`; makes the game in `./<name>` and prints the next steps for the package manager in `npm_config_user_agent`. |
| `examples/showcase` | Small Town: the game that uses every feature. Its tests play it; the docs point at its source. |
| `examples/novel` | The Letter: a linear novel with no plugins, places or clock, the smallest shape of game. |
| `games/` | Not in git: users' own games, made by `npm run new -- <name>`, as workspaces of the checkout. |
| `examples/cafe` | The Corner Café: a management game a week at a time, with staff and dishes as entities. |

Every game, template and example lays out its source the same way: `src/game.ts` only assembles (`loadGame(content, base, { packs })`, with the plugins and rules), `src/rules.ts` holds the game's rules and custom functions, `src/world/` holds what the whole game shares as one `Content` file per kind (`stats.ts`, `things.ts`, `cast.ts`, ...), and `src/story/` one per area, a place, chapter or arc (`story/cafe.ts`), with its scenes, prose (or a sibling `<area>.prose.ts`) and its slice of plugin content. Keep new example content in that layout; the docs page is `guide/organising.md`, and `loadGame` reports a key the content declares twice. Packs (mods, `src/unlocks/` content) go in `packs`, over the content.

A first-party plugin is a package of its own that imports only `@ifloom/engine` (its `tests/contracts/boundary.test.ts` holds it to that) and requires no other plugin. It may work with others when the game has them, by name only: it lists them in `cooperates` and asks them through conditions, effects and `query`. It is documented under `site/content/docs/(latest)/plugins/`, and a docs contract fails on any export the page does not name.

## How packages depend on each other

- **An `@ifloom/*` package another one uses is its peer dependency, never a dependency.** A plugin peers on the engine, `@ifloom/phone` on the plugins it wires, and `@ifloom/react` on the engine, `@ifloom/audio`, `@ifloom/browser` and, as optional peers, the plugins whose view types it reads. So a game has one copy of each, at the version it chose. npm 7 and later installs a required peer the game doesn't list.
- **Every reference to an `@ifloom/*` package is `^` and its version**, `^0.0.0` for now: in peers and dev dependencies, the examples, the templates, the site and the docs' snippets. A caret on `0.0.x` matches that version only, on `0.x` the same minor, and from 1.0 the same major, so it accepts what semver calls compatible. A release bumps the versions and the ranges together.
- **Other libraries:** what a package runs on its own (Radix, `clsx`) is a dependency. What the game's build or typecheck must share with it is a peer: `react`, `react-dom`, `tailwindcss` and React's types for `@ifloom/react`, whose `.d.ts` files a game's typecheck reads. A game lists its framework's Vite plugins itself.
- `create-ifloom` is the one package that uses another without peering on it: `@ifloom/cli` is a dev dependency it bundles at build time, since an initializer has to run on its own.
- `packages/cli/tests/contracts/packages.test.ts` holds the first two rules, and the packaging below.

## Packaging

Every package builds with tsdown to `dist/` (ESM `.js`, `.d.ts`, declaration and source maps), and nothing in the checkout reads it.

- **Exports.** Each entry is `{ "ifloom-source": "./src/x.ts", "types": "./dist/x.d.ts", "import": "./dist/x.js", "default": "./dist/x.js" }`, and `files` is `["dist", "src"]`. A package has `"build": "tsdown"` and a `tsdown.config.ts` that calls `define([...entries])` from `tsdown.base.ts`. `@ifloom/react`'s build also writes `styles.min.css` and `themes/<preset>.min.css` with the Tailwind CLI. The CLI's `bin` is `bin.js`, which imports `#bin`: `src/bin.ts` under the condition, `dist/bin.js` otherwise. create-ifloom's `bin` works the same way, and it has no `exports`.
- **The source condition.** The checkout's tools resolve `ifloom-source`, so they run `src/` with no build: Vitest (`vitest.config.ts`), tsc (`customConditions` in `tsconfig.base.json` and `site/tsconfig.json`), the Vite preset for a game inside the checkout (`packages/cli/src/source.ts`, which also loads its `vite.config.ts` natively), Node through `.npmrc`'s `node-options` (so `npx ifloom` runs the CLI's source too, which needs Node 22.18 or later to strip the types), and the site through `turbopack.resolveAlias` in `site/next.config.mjs`. A test that starts Vite on a fixture passes `configLoader: 'native'`. Anything outside the checkout gets `dist/`. So a change to a package shows up straight away in the examples and in `games/*`, except a `next` game: Next has no setting for the condition, so run `npm run build` before its `dev` or `build`, and again after changing a package.
- **Building.** `npm run build` builds every package, each after the @ifloom packages it uses; `npm run pack` also packs each into `packs/` for a game beside the checkout (`scripts/pack.ts`). `scripts/try-dist.sh` builds, imports every export from `dist/` in plain Node and type-checks a consumer against the `.d.ts` files; run it when a package's entries, exports or build change.

`packages/engine/tests/fixtures/` holds a small town game with no story; engine tests run against it. The showcase is `examples/showcase`.

## Rules the engine keeps

- **Deterministic.** Every draw goes through `random.ts`, hashed from the save's seed, the turn and a name. Same save, same cards.
- **Nothing loads at runtime.** Everything a game needs is bundled when it is built, because a game opened from disk can fetch nothing. `tests/contracts/boundary.test.ts` enforces it.
- **No genre, no game.** The engine knows no stat, phase, place or person by name; a game declares them and supplies its own logic through `pack.rules`. Examples, comments and docs use everyday, neutral fiction.
- **Standalone.** The engine imports nothing outside its own folder.
- **One naming rule for content**. A condition's or effect's target is named by its noun (`stat`, `entity`, `storyline`, `scene`; `key` in a kv store), `by` changes a number and `to` sets a value, and a command names its one target `id`. Plugin kinds follow it too. `tests/contracts/naming.test.ts` holds every kind to it.
- **One plugin shape**. A hook runs at an event and returns the next state, named `onX` (`onTurn`, `onCommand`, and the game's `rules.onTurn`, `rules.onTurnDone`, `rules.onStat`); a provider answers and changes nothing, named by its noun (`guard`, `label`, `view`, `profile`); nothing is nested. A plugin call's short form takes its arguments as an object, `{ 'places/at': { location } }`, and every helper writes it. Values take arguments. Anything a mod could change is content in pack `data`, never a plugin option. `tests/contracts/plugin-shape.test.ts` holds the first-party plugins to it.
- **One separator rule for ids**. An id is letters, digits, `-` and `_`, in parts joined by `.` (`cafe.counter`, `place.cafe.ava`); `/` names a plugin (`quests/done`, `calendar/period.morning`); `#` is a choice in a scene or a reply (`ch1.mat#open`, in labels, `chose` and `state.chosen`); `:` is a reference with what it is in front (`character:ava`, `mod:naps`, the profile's `core:settings` and `ui:gate`). `tests/contracts/ids.test.ts` holds the examples, the templates and the showcase's plugin content to it.
- **Framework-neutral.** The engine and plugins import no UI framework; React lives only in `@ifloom/react`, and the CLI and its Vite preset name no framework: each game's `vite.config.ts` adds its own framework's plugin (and Tailwind for the React UI). The `vanilla` template proves a game runs without React.

## Words

Author-facing words, used in docs and new API: scene, choice, action, location, character, storyline, stage, stat, kv (the kv store: keys with a true/false, number or text value; never "flags" or "variables"), blocked (why something can be refused: `{ when, reason, hide? }`, refused while `when` holds; never "requires" or "locked"), effects, cost, once/cooldown, turn, kind, entity (what it is lives in content, its name, `desc`, `image`, `tags`, traits and starting stats and kv; the save keeps only what play changed, and reads fall back to content; never copy a definition into a save), trait (a named piece of data an entity carries, never functions: written on a kind as a default, on an entity, or in a content or pack `traits` table, row over the entity's own over the kind's, and read with `traitOf`, or `entityTrait` for one made in play `like` another; an id with a `/` is a plugin's, which declares it in its `traits` and types it by augmenting `interface Traits`, and one without is the game's), listed (whether the view shows a kind's entities: a kind's `listed`, true, false or a condition with `'$'` as each entity, narrowed by an entity's `visible`; the engine filters, so nothing unlisted reaches the view, and a UI splits what's listed by a kind's `marks` rather than hiding more; a game's kinds are listed by default, a plugin's are not), holder and held (a holder is who has things: `'player'`, a unique entity, or `'you'`; what a holder has is what it holds, and `held` is the save's record of counts play changed, read over each entity's `at` in content; only unique entities hold, other kinds stack, and nothing holds itself), you (`'you'` is whoever the player is playing now: the protagonist the `you` effect chose, else `'player'`; never call it "the current character" or "the active player"), trigger, lock, variants, block, tag, thing (anything a game keeps that the player can hold or collect, such as a sandwich, a note or a photo: an entity, held by a holder; never "item", which the engine no longer has, nor "collection"), save, mod. Developer words: plugin, content and pack (content is the game's own, in its files: a `Content` with no id or schema, each key declared once across it, never upgraded; a pack is what comes from outside the code, a mod, unlocked content or a JSON export: a `Pack` with an `id` that saves record, a `schema` that `upgradePack` carries forward, and optional `patches`, laid over the content last-wins; never call the game's own files packs), hook (a plugin's or the game's `onX`, run at an event, returning the next state), provider (a plugin member that answers a question and changes nothing, named by its noun: `guard`, `price`, `label`, `stage`, `view`, `profile`), options (a plugin factory's settings, code a mod can't change; content goes in `data`), panel (a named piece of UI over the story that content opens with the `panel` effect and the UI draws by name, such as `shop` or `jobs`, kept in `state.panel` until `closePanel`, a turn ending or the scene changing; also a game's own UI component, named in `panels`, which can stand for one; the React UI's built-in boxes are cards: `LocationCard`, `DebugCard`), view, state slice, snapshot, content checker (`checkGame`, the one walk that checks a game's content and lists the files it names), references (what a condition, effect, command or plugin's content names, from each kind's `references` entry and a plugin's `references`), content migrations (`upgradePack` in `upgrade.ts`, the one way a pack written for an older `SCHEMA` comes in: its `PACK_STEPS`, one per schema change keyed by the schema it upgrades from, as `STEPS` in `intake.ts` are for saves; `loadGame`'s `packs`, `readMod` and the editor's JSON import all go through it, and content never does), state intake (`loadState`, the one way a state from outside, such as a save, comes into play: the engine's steps, the plugins' and the game's migrations, then what the game declares; a new game comes from `startingState`, and both read each field's defaults from `FIELDS` in `intake.ts`, which holds the core's fields and each feature's `state`). Result (`Result<T>`, `{ ok: true, value } | { ok: false, reason }`: what the runner, the save and mod stores, `loadState`, `replay`, `readMod` and `upgradePack` answer when something can fail in a way a caller should expect; they never throw for those, and the engine's `apply` gives the same shape with the state on both sides; `checkGame`'s problems are a report, not a failure). Feature (a core feature, such as scenes, stats, entities, holdings or triggers: each one module in `src/features/` that declares its state, kinds, pack key, checks and the references it resolves, view piece, after-command steps, fills and carries; never a plugin), `defineFeature` (how a core feature is declared; internal, not exported). `screen` (`screen(state, game)`, one state drawn once: the open scene or the room, its choices with their effects, availability and price, the stage, the plugins' views, and the pool picks and audio they imply; `view` formats it into what every UI draws, worded and free of spoilers such as a choice's effects, and the reducer records picks and audio from it, so each state is drawn once). Page, in the React UI only: the title screen and the pages around the game (settings, load, credits, the gate and any a game adds), turned on with the `pages` option. Never call those screens, so `screen` keeps one meaning. Layout, story and section, in the React UI only: the layout is the page as a component (`src/layout.tsx`, `DefaultLayout`) made of regions (`Game`, `Sidebar`, `Story`, `Overlay`); the story is the main column (`data-part="story"`), never "stage", which is only the layered picture; a section is a titled `Section` of a layout that folds (`collapsible`) or opens in a dialog (`dialog`). The code uses these words too (storyline, character, `View`, `Game`, `Content`, `Pack`, stages, blocks, variants); `site/content/docs/(latest)/guide/status.md` lists the few renames still to come.

Every user-visible change adds a line to `CHANGELOG.md`, under `[Unreleased]` in Added, Changed, Removed or Fixed. Write it for someone making a game, not as a commit message. The docs show it at `/docs/changelog`.

## Adding to the core

A core kind of condition, effect or command, or a field of the state, belongs to a feature in `packages/engine/src/features/`. To add one:

1. Add its type to the feature's shape (`SettingsShape`, say) and its entry to the matching table in the feature's `defineFeature`. The public `Condition`, `Effect`, `Command`, `GameState`, `Game`, `Content`, `Pack` and `View` are built from the shapes, so there's nothing else to edit. A new kind of `Reference` gets its resolver in the feature's `resolve`.
2. For a new feature, write the module with `defineFeature`, then add it to `FEATURES` and its shape to `Shapes` in `features/registry.ts`. Where it goes in `FEATURES` matters: its after-command steps, checks and fills run in that order.
3. Keep the feature a leaf. Import only types, other features, `strings`, `entities`, `holdings`, `notices`, `storylines`, `context`, `range` and `sceneBody`; take everything else (`holds`, `runEffects`, `buildEffects`, `weighted` and the rest) from the `FeatureContext` argument. `tests/contracts/features.test.ts` fails otherwise.
4. A helper the engine exports that needs the core (`activityBlocked`, `lockedBy`, `fireTriggers`, `statValue`) stays in its module outside `features/` (`activity.ts`, `locks.ts`), which binds the core's context and calls the feature's version.
5. `src/core.ts` keeps only the kinds that are no feature's: `all`, `any`, `not`, the custom calls and `start`.

## Docs

Anything the engine exports is documented in `site/content/docs/`, the docs part of the website in `site/` (Next.js with Fumadocs, published at https://ifloom.dev, with the docs under `/docs/`). A change to the exports ships with its docs in the same change. The homepage is React, in `site/components/home/`. The editor at `/editor` is a client-only React app: its routes are in `site/app/editor/`, and its code in `site/editor/`, with the pure logic in `site/editor/lib/` tested by `npm test`.

The pages are plain Markdown (`.md`) with a `title` and a `description` in front matter, and links between pages are absolute: `[Scenes](/docs/reference/scenes#scene)`. Each folder's `meta.json` gives the sidebar's order, and each section is a tab: the Guide (tutorials, read in order: an Engine track that uses the engine as a library, then a UI track), Recipes (how to build one piece, such as a HUD or a title screen, and how to build with Next, webpack or esbuild), the Reference (the engine's exports), Plugins, Browser (`@ifloom/browser` and `@ifloom/audio`), the React UI, the CLI and the changelog. A page that moves gets a redirect in `MOVED` in `site/next.config.mjs`, for the page and its Markdown under `/llms.mdx/`. `npm run docs:links` fails on a link to a page or heading that isn't there.

The docs are versioned: `site/content/docs/(latest)/` holds the latest docs, and each other folder there is a released version, served at `/docs/<version>/`. Don't edit a released version except to fix something that was wrong in it.

## Verify

```bash
npm test             # engine tests, boundary rules, docs coverage
npm run check        # the format and lint (vp check), then npm run typecheck; any lint warning fails
npm run typecheck    # strict: tsc on each package, example and the site
npm run format       # rewrites the code in the repo's format (Oxfmt)
npm run docs:build   # checks the links, then builds the site (next build)
```

The checkout's own tools run through [Vite+](https://viteplus.dev) (`vite-plus`, a dev dependency of the root only): the task runner `vp run`, Oxfmt and Oxlint. The root `vite.config.ts` holds their settings and the tasks: `build:<package>`, `typecheck:<project>`, `test:all`, and `site:links` and `site:build` for the docs site, run by `npm run build`, `npm run typecheck`, `npm test` and `npm run docs:build`. A task is cached by the files it read, so it runs again only when one of them changes, and a cached build puts `dist/` back. The site's two tasks list their files by hand instead: `site/`, the source of the packages the site depends on, the changelog and the root's `package.json`, lockfile and `.npmrc`, so an edit to the CLI, a test or an example doesn't rebuild the site, and a cached `site:build` puts `site/.next/` back without Next's own cache. `npx vp run typecheck:plugin-shop` runs one task, and `npx vp cache clean` empties the cache. The format is the code only, at 160 columns: Markdown, JSON, CSS, HTML and YAML keep their hand-made shape. Oxlint also runs its type-aware rules (tsgolint, `typeAware` in the `lint` block) over every project but the CLI's templates, and any warning fails the check; the `lint` block says which rules are off and why. The typecheck itself stays on tsc. Nothing a game, a template or a package's user gets depends on Vite+; the CLI builds games with plain Vite.

`scripts/verify.sh` runs `npm test`, `npm run check`, the docs build, and the examples' check, build and snapshot, all from `src/`. `scripts/try-dist.sh` checks the built packages (see Packaging). `scripts/try-templates.sh [--pm npm|pnpm|yarn|bun|all]` packs the packages, makes a game from each of the `react`, `vue`, `svelte`, `vanilla` and `next` templates (and a package from `plugin`) in a temporary folder outside the checkout, installs the tarballs with that package manager, and runs its check, playtest, build and typecheck. With each package manager it also makes one game with create-ifloom's bin from its tarball (`--create <template>`, `react` by default). Run it when a template, the Vite preset, the build, create-ifloom or a package's dependencies change.

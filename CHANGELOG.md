# Changelog

Every change you'd notice as someone making a game with IFLoom is listed here, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions will follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html) once there is a first release.

IFLoom is pre-release, so nothing is a stable API yet and anything below can still change.

## [Unreleased]

**Things are entities.** The engine no longer has items or collections of its own. A sandwich, a scarf, a note, a photo, a person and a place are all [entities](/docs/reference/entities) of a kind: what each is stays in your content, and the save keeps only what play changed. Kinds can be `unique` and say whether they're `listed`. Entities carry [traits](/docs/reference/entities#traits) that plugins read. The player and unique entities [hold](/docs/reference/entities#holding-things) things, and `'you'` is whoever the player is playing. The inventory, shop, wardrobe, cast, places and generators all work on them, alone or together (see [Things: carrying, selling, wearing](/docs/recipes/things)). Old saves, packs and mods are carried forward; your own content isn't, so `ifloom check` reports what to rewrite. The details are in the lists below.

### Added

- [Typed calls, queries and views](/docs/reference/plugins#typed-calls-queries-and-views): a plugin declares what each of its calls takes, what its queries answer and what its view holds, by adding to the engine's `ConditionRegistry`, `EffectRegistry`, `CommandRegistry`, `QueryRegistry` and `ViewRegistry`, as it types its traits. In code, `{ 'quests/done': { qeust: 'bread' } }` now fails to compile, `context.query('calendar/now')` is a `CalendarState`, and `view.plugins.shop` is a `ShopView`. Every first-party plugin declares all of its own, and so does the plugin template. A call nobody declares still takes any arguments, so a third-party plugin that declares nothing still compiles.
- Your game can declare its own `game/…` calls the same way, beside its `rules`. Small Town and the café do.

- [Amounts](/docs/reference/amounts): most places that take a number also take an `Amount`, a number worked out in play. It's a number, a stat (`'rent'` or `{ stat, of }`), a [formula](/docs/reference/stats#formula), a kv key's number (`{ kv, of }`), a value by name (`{ value, with }`) or a count of entities (`{ count }`). So "coins at least the rent" is `{ stat: 'coins', gte: { stat: 'rent' } }`, with no code. Range bounds take one, as do a `stat` effect's `by` and `to`, a `kv` effect's `by` and `random`, the `entity` and `move` effects' `by`, a stat's `min` and `max`, and a roll's `plus` and `against`. [`amountOf(state, game, amount)`](/docs/reference/amounts#amountof) reads one, and the checker reports one naming a stat, kv owner or value the game doesn't have.
- An achievement's progress `value` and a device app's `badge` take any `Amount`, so a badge can count a kv key or a stat.
- [`inRange`](/docs/reference/conditions#inrange) takes the state and the game, to work out a bound that is an amount.

- The React UI shows who says a spoken line in a small label over its words, the `speaker-name` part: the speaker's name from their entity, or on the player's own lines the name the save is listed under (`rules.saveName`), else `You`. A quote that answers the line before names no one, and narration has no label. Each preset styles it, and `[data-part="speaker-name"] { display: none }` hides it. The vanilla, Vue and Svelte templates show it too, as `.speaker-name`.

- [Flowing scenes](/docs/reference/flows): a scene's body can stop partway through at a decision, `decide('order', [choice('tea', 'A pot of tea', { then: [...] }), ...])`, and once the player picks, the pick's `then` comes next and the scene reads on after it, the earlier text still on the page with a `chose` beat where the pick was. A `point()` marks a place a choice can go to with `jump()`, so questions can be asked in any order. A point can sit anywhere, in a section or a pick's `then` too, so a jump can also skip ahead, and the flow reads on from the point. Sections show under a `when()`, a minigame or a panel is played where it stands and the flow waits for it, and `fold()` makes a part the player opens and shuts. Words go in place with `text()`, which takes off shared indentation, and `say(who, words)`. The builders are exported from `@ifloom/engine` and return plain data. The save keeps the visit's path in `state.flow` (older saves load with none), every pick is a logged `choose`, so replay, undo and the backlog are exact, and the checker reports duplicate ids, a jump to nowhere, a decision that can get stuck and text that can't be reached. See [Writing a flowing scene](/docs/recipes/flowing-scenes).
- `view.scene.fresh` is the first beat the last pick brought, so a UI can animate only the new text. A beat in a section with hints carries them as `section`.
- The React UI draws a past pick small and set in, and a `fold()` as a part that opens and shuts (the [`fold`](/docs/react/hints#fold) hint). The templates draw a past pick too.
- Small Town's evening by the river is a flowing scene: pocket a shell and ask about the ducks before you sit with Ava. The Letter's second chapter reads on from the answer you give Mrs Okafor.

- A scene's choice can have a `cost`, `{ stats: { coins: 2 } }`, as an action can: shown as its price, checked when it's chosen, and paid after its command. An action can have `labels`, `tags` and `irreversible`, as a choice can. Both are a [`ButtonDef`](/docs/reference/actions#buttondef).
- A choice's `label` can be the words themselves, `label: 'Buy a slice of cake'`. A prose key still works when the game's prose has it, and so for an action's.

- A plugin's context has [`beats(blocks, id)`](/docs/reference/plugins#beats), which draws a scene's kind of blocks as beats, as a scene's body is drawn: `when`s, tokens, variants, pool picks recorded, spoken lines with their speakers, and bold, italics and UI pieces. The game's own code gets it too. The messages, feed and devices plugins draw their words with it.
- A spoken line names who says it by id, as a scene's speaker is named: `@ava: "Morning."` gives `{ type: 'say', who: 'character', speaker: 'character:ava', name: 'Ava', text }`, so a UI can tell her lines from Sam's. A full reference works too, `@staff:dev:`. `@you:` is whoever the player is playing, and `@player:` the player. The beat's `name` comes from the entity, so a renamed or translated character reads right everywhere, and the player's lines show the name their saves are listed under (`rules.saveName`), else the string [`you`](/docs/reference/strings#buttons-and-labels). The checker reports an id that names no entity. See [Speech](/docs/reference/prose#speech).
- [`speakerOf(state, game, id)`](/docs/reference/plugins#speakerof) says who an id is, as a scene's speaker is shown: the entity's name, picture and hints, or `null`.
- The React UI draws three more [inline pieces](/docs/react/hints#inline-pieces): `[[ui:mail|body|From: Ava|Subject: Hi]]` a letter, `[[ui:prop|words|sticky]]` a note (`sticky`, `clip` or `diary`) and `[[ui:mono|words]]` a sign in a monospace face, as [`InlineMail`](/docs/react/components#inlinemail), [`InlineProp`](/docs/react/components#inlineprop) and [`InlineMono`](/docs/react/components#inlinemono). A UI piece's words can run over blank lines.
- The React UI's [`tilt`](/docs/react/hints#tilt) block hint sets a picture at a slight angle.

- A plugin can bring content of its own in `content`, a [`Content`](/docs/reference/loader#content) merged first, under the game's content and packs, which can replace anything in it by id. Its kinds stay unlisted unless it says. The cast's `character` kind, the places plugin's `location` kind and the shop's `vendor` kind come this way.
- A lock can have an `id`, so a pack can replace it: a pack's lock with the same id takes its place.
- Content can give the kv store a new game starts with, `kv: { phase: 'arrival', lives: 3 }`, declared once per key across the content; a pack's value replaces the content's. `startingState`'s `kv` still goes over it.
- The game's own code, [`rules`](/docs/reference/rules), can have everything a plugin can, with no plugin to write: `conditions`, `effects`, `values`, `queries` and `commands` content calls, and the hooks and providers `onCommand`, `guard`, `price`, `label`, `stage`, `buttons`, `statModifiers`, `audio`, `view` and `profile`. Content calls them as it calls a plugin's, with `game` in front: `{ 'game/tired': true }`, `{ 'game/postLatest': {} }`, `{{v:game/catName}}`, a command `{ 'game/rest': true }`. Its view is at `view.plugins.game`. The game's code runs before every plugin's, as if it were the first one. Its hooks and commands are handed a [`RulesContext`](/docs/reference/rules#rulescontext), and a command is a [`RulesCommand`](/docs/reference/rules#rulescommand).
- An action can be once a turn, `once: { per: 'turn', reason: 'Once is enough today.' }`, as a choice can.
- [`actionReferences`](/docs/reference/actions#actionreferences) gives what an action names, for a plugin whose content holds actions to hand to its `references`. A plugin can answer for an action that isn't among its buttons with [`action`](/docs/reference/plugins#action), as the devices plugin does for an app's buttons.
- Plugins have `onTurnDone` and `onStat` hooks, as the game does. A turn ends with the game's `onTurn`, every plugin's `onTurn`, the game's `onTurnDone`, then every plugin's `onTurnDone`. A stat change goes through the game's `onStat`, then each plugin's.
- A plugin carries its own content and commands forward. `contentVersion` and `contentMigrations` say what content written for an older version of the plugin looked like and how to rewrite it, and `commandVersion` and `commandMigrations` do the same for its commands in old command logs. A community plugin can rename an argument or reshape its `data` in a release, and packs and mods written for the last one still load. Each step is handed the pack and [`ContentTools`](/docs/reference/plugins#contenttools) to rewrite every call, object or line of words in it. See [Content and command migrations](/docs/reference/plugins#content-and-command-migrations).
- A pack records the version of each plugin's content it was written for in `plugins`, beside `schema`: `{ id: 'mod:sunday', schema: SCHEMA, plugins: { shop: 13 } }`. A pack that leaves a plugin out is read as written for its schema, or for the plugin's own version if that's lower. A pack written for a newer version of a plugin than the game has is skipped with a problem.
- A runner's command log records `schema` and each plugin's command version, so `replay` runs only the steps an old log needs.
- Each plugin with something for the player ships its own React UI, in a subpath of its package: `@ifloom/plugin-shop/react`, `@ifloom/plugin-quests/react` and the rest. List the ones you want in the new `plugins` option of `mountGame`, `GameShell` or `GameProvider`, `mountGame(game, { plugins: [questsUi, shopUi] })`, and each brings its panels, its words, its page or settings, and the parts the default layout places. Leave a plugin out and draw it yourself from `view.plugins.<id>` or its hooks. See [Plugin UIs and the kit](/docs/react/kit).
- `<Plugins at="sidebar" />` in a layout of your own places what the listed plugin UIs bring there (`stats`, `sidebar`, `room`, `story`, `strip`), in the order of the list. The react and next templates' `src/layout.tsx` has one at each spot.
- A plugin's React UI is a `PluginUi`, a plain object, so `{ ...achievementsUi, pages: undefined }` leaves out what you don't want. A plugin of your own can ship one the same way: `ifloom new --template plugin` now starts a plugin with its `/react` subpath and a test that draws it.
- The kit, the parts of `@ifloom/react` a plugin's UI (or your own) is built from, now documented and exported in full: `usePriceText`, `useDialogParts`, `DIALOG_CLASSES`, `StatGauge`, `PageHeading`, `BackButton`, `usePageParts`, `PROSE` and `ENTRY_CLASSES`, beside `useGame`, `ChoiceButton`, `PartDialog`, `Section` and the rest. `useWords(table)` and `uiSay(game, key, vars, table)` say a plugin UI's own words, which a game rewords with `ui.<key>` as before.
- `data-kit` on the parts a plugin's UI draws, saying what each is like: a good, a job and an achievement are each a `card`, their names a `title`. Style `[data-kit="card"]` to restyle every card at once. `useKitPart` gives a part of your own one.
- The calendar's UI draws the clock with `data-day`, `data-weekday`, `data-period` and `data-curfew` on it, for a stylesheet.

- [Dice rolls](/docs/reference/rolls): the `roll` effect, `{ roll: 'skim', dice: '2d6', against: 8 }`, throws dice in notation (`'1d20'`, `'2d6+1'`, `'d100'`) or as `{ count, sides }`, adds a number or a stat with `plus: { stat: 'strength' }`, and keeps the total in the kv store under its key, so `{{skim}}` prints it. Every roll is seeded from the save and replays exactly, and trying again rolls afresh. The `roll` condition reads how it went, `{ roll: 'skim', passed: true }` or `critical: 'max'`, and `view.rolls` lists the last command's rolls with their faces for a UI to show. The checker reports dice it can't read, a die with fewer than 2 sides, an unknown stat and a key `{{key}}` couldn't print. See the recipe [Dice rolls and checks](/docs/recipes/dice).
- The React UI's [`dice` hint](/docs/react/hints#dice): `ui: { dice: 'skim' }` on a block draws that roll's [`DiceRoll`](/docs/react/components#diceroll) above it, tumbling and then settling, with the total and Passed or Failed, and holds the block back until the dice land. Rolls no block names, such as a trigger's, show for a moment in a [`DiceOverlay`](/docs/react/components#diceoverlay). Reduced motion shows them settled, and a screen reader hears the result. Each theme preset draws dice its own way.
- [Timers](/docs/reference/timers): named countdowns in real time. Declare one in `timers` with its length and the effects that run when it runs out, `{ id: 'phone', ms: 10_000, effects: [...] }`, then start it with `{ timer: 'phone' }`, stop it without its effects with `to: null`, or add time with `by`. `{ timer: 'phone' }` holds while it runs and `{ timer: 'phone', lte: 3000 }` in its last three seconds. `view.timers` lists each running timer's time left and length for a countdown, and never what it does. Time passes by the logged `tick` command, so replays run every timer out at the same moment; the save keeps only the time left. Old saves load with no timers running. See the recipe [Timed choices and countdowns](/docs/recipes/timers).
- The React UI's [`timer` hint](/docs/react/hints#timer): `ui: { timer: 'phone' }` on a block draws a [`Countdown`](/docs/react/components#countdown) under it while the timer runs, with its label, a bar and the seconds left, marked urgent in the last quarter. Reduced motion shows the seconds only. Place `Countdown` or `Timers` in a layout to show timers anywhere else, or read them with `useTimer` and `useTimers`. Each theme preset draws them its own way.
- [UI pieces in prose](/docs/reference/prose#ui-pieces): write `[[ui:name|words|arg]]` inside a paragraph, in narration or a spoken line, and the view hands your UI a `ui` span with the name, the words and the arguments, as written. The engine gives it no meaning, and the words stay in the beat's text for screen readers, the backlog and the playtest. A UI types its names and arguments by adding to [`InlineUi`](/docs/reference/ui-hints#inlineui). The checker reports a piece with no name or no words, a name that isn't an id, an empty argument and markup that isn't closed.
- The React UI draws two UI pieces: `[[ui:modal|the note|notice.welcome]]` opens a dialog with a prose line, and `[[ui:image|her photo|photo/ava.svg]]` opens a picture in the viewer. Give `mountGame` or `GameProvider` an [`inline`](/docs/react/hints#inline-pieces) object to draw names of your own, or to replace these. A name nothing draws shows its words. Both are buttons that open a dialog, close on Escape and give focus back, and each theme preset styles them. [`checkUiHints`](/docs/react/hints#checkuihints) now reads the prose too, and reports a piece the UI can't draw, a modal whose prose is missing and an image with no path.
- A recipe, [Popups and modals](/docs/recipes/modals): a popup that only shows words with `[[ui:modal|…]]`, and a modal whose buttons change the game with an inline action and the `panel` effect, in the React UI, plain DOM, React and Vue.
- Small Town's flat opens Sam's welcome note from "the radiator knocks", and Ava's name at the café opens her photo.
- Small Town's phone rings at home one evening after you've answered Ava's text: answer within ten seconds, or it's a missed call.
- Small Town's park has stones to skim, a check on two dice against 8 from a link in the prose, and counts the ducks as you arrive.
- [Presentation hints](/docs/reference/ui-hints): a `ui` field on scenes, choices, blocks, actions, stats, kinds, entities, places and the game. The engine passes it to the view as written (`view.scene.ui`, a choice's `ui`, the first beat of a block, a stat's, an entity's, a speaker's) and only checks it's data. A UI package gives the hints meaning and types them by adding to `SceneUi`, `ChoiceUi`, `BlockUi`, `StatUi`, `EntityUi` and `GameUi`. [`entityUi`](/docs/reference/ui-hints#entityui) reads an entity's hints over its kind's.
- `view.scene.key` says which screen is on show (`scene:<id>`, `minigame:<id>`, `room:<id>`), and changes only when the screen does.
- The React UI's [hint vocabulary](/docs/react/hints): `transition` on a scene, a place or the game, `transition` on a choice for how the screen it leads to comes in (by a click or a number key), `reveal` on a block, `display` on a stat, and `hue` on an entity, which now colours a speaker's lines. [`checkUiHints(game)`](/docs/react/hints#checkuihints) reports a hint it doesn't know, a transition name the game hasn't listed, a pips stat with too wide a range and the like; put it in a test.
- A recipe, [Things: carrying, selling, wearing](/docs/recipes/things): which plugin does what with the things a player holds, alone or together. The concepts guide and How the pieces fit explain kinds, traits, holders and `'you'`.
- Every place of the [places plugin](/docs/plugins/places#each-place-is-an-entity) is a unique entity of the kind `location` (`location('park')` is `'location:park'`), so a thing can lie in a room: write `at: 'location:hall'` on it, or drop it there. The places view lists what lies where the player is, with a **Pick up** button each (`pickUp(ref)`, the `places/pickUp` command), and the React UI's `LocationCard` draws them. Places answers `places/holder`, so the inventory's `drop` now puts a thing down in the room instead of losing it.
- [Generator templates](/docs/plugins/generators#templatedef) take the rest of `create`'s fields: `like`, `desc`, `image` (drawn as the name is), `tags`, `traits` and `at`. With `like`, `of` and `name` can be left out. A drawn stat that's what the entity would read anyway isn't kept in the save. Draws for the fields a template already had are unchanged, so old seeds make the same people.
- The wardrobe's `wardrobe/wearing` takes `at`, to ask about the player's or a protagonist's clothes rather than whoever is played now.
- A trait's `references` gets the entity it's on (`tools.ref`), as `check` does, so a trait can bind `'$'` in its conditions.
- A stat's `format` and `lacking` can give one line for 1 and one for any other number, `{ one: '{n} coin', other: '{n} coins' }`, so a price reads "1 coin" and "4 coins". See [`StatWords`](/docs/reference/stats#statwords).
- [`create`](/docs/reference/effects#create) gives the thing it makes a `desc` and an `image`, so a photo the player takes or a note they write has its own words and picture.
- The devices plugin's `{ things: { of, at? } }` section lists the things of a kind you hold, newest first, such as photos or notes.
- `carryOver.held` for New Game+: the things the player held, by reference, or `'all'`. A thing made in play, such as a photo, comes with them.
- The debug plugin's `debug/held` (`debugHeld(entity, to, at?)`) sets how many of a thing someone holds.
- [`@ifloom/plugin-inventory`](/docs/plugins/inventory): use, drop and give away the things you hold. Give a thing the `inventory/usable` trait with `usable('Eat the sandwich', effects)` and it gets a button that runs its effects and spends one, or keeps it with `keep: true`. `giveThing(ref, 'character:ava')` hands one to someone. The React UI's `Inventory` draws its buttons, and `useInventory` gives them with no markup.
- The shop's `shop/sellable` trait (`sellable({ coins: 4 })`): a thing's price for every vendor that lists it without one, on a kind, an entity or a mod's `traits` table.
- The wardrobe's `wardrobe/wearable` trait (`wearable('coat')`): the slot a thing is worn in.
- [`isUnique`](/docs/reference/entities#isunique), and a `game` in [`MigrationTools`](/docs/reference/saves#migrationtools), for a migration step that needs to look up content. The checker's `{ entity }` reference reports a plugin's content naming an entity nobody declares.
- The React UI's `Inventory` lists what you hold (`view.held`), with the inventory plugin's buttons when the game has it, and a drop button with `drop`. `ShopCounter` shows a good's picture and description.

- Holding things: the player and unique entities hold things, such as two apples in your pocket or a scarf Ava keeps. An entity's `at` says who holds it at the start, the [`entity`](/docs/reference/effects#entity) effect gives and takes, [`move`](/docs/reference/effects#move) moves a thing from one holder to another, and [`{ entity, at }`](/docs/reference/conditions#entity) asks how many someone holds. Kinds that aren't `unique` stack, and a unique thing is in one place at a time. The save keeps only counts play changed, so a thing an update places reaches old saves. See [Holding things](/docs/reference/entities#holding-things).
- `'you'`, whoever the player is playing now: a holder, and an `of` for stats and kv keys. A game with several protagonists switches with the [`you`](/docs/reference/effects#you) effect, and one with a single protagonist never needs to, so `'you'` is the player.
- [`{ count }`](/docs/reference/conditions#count) takes a [`Select`](/docs/reference/entities#select) (`of`, `at`, `tag`, `trait`, `where`) as well as a kind, and `units: true` to count how many are held rather than how many different things. [`each`](/docs/reference/effects#each) takes `at`, `tag` and `trait` too, and its `of` is optional.
- [`create`](/docs/reference/effects#create) takes `like`, to make a thing that reads what it isn't given from another entity, `at` to give it to someone, and `tags` and `traits` for the new entity.
- `view.held`, what you hold, ready for a UI to draw: names, descriptions, pictures, tags and counts.
- Helpers [`give`, `take`, `move` and `holding`](/docs/reference/entities#give-take-move-and-holding), and functions [`heldCount`](/docs/reference/entities#heldcount), [`heldBy`](/docs/reference/entities#heldby), [`holderOf`](/docs/reference/entities#holderof-and-holdersof), [`entityTrait`](/docs/reference/entities#entitytrait) and more for plugins and custom code.
- Traits: named data an entity carries, such as how a coat is washed, for a plugin or your own code to read with [`traitOf`](/docs/reference/entities#traitof) and [`withTrait`](/docs/reference/entities#withtrait). Write them on a kind as defaults, on an entity, or in a new `traits` table in content or a pack, which lets a mod give an entity a trait without redeclaring it. A plugin declares the traits it reads in its `traits`, types them by adding to the engine's `TraitRegistry` interface, and checks them with the rest of the game. See [Traits](/docs/reference/entities#traits).
- An entity can have a `desc`, an `image` and `tags`, and a `visible` condition that decides whether the view lists it. [`entityName`](/docs/reference/entities#entityname), [`entityDesc`](/docs/reference/entities#entitydesc), [`entityKv`](/docs/reference/entities#entitykv) and [`entityTags`](/docs/reference/entities#entitytags) read them, names and descriptions with their prose tokens filled. The React UI's `EntityTable` shows the picture and description when there are any.
- A kind can be `unique` (each entity one particular thing, such as a person), have `tags` every entity of it shares, decide what the view lists with `listed` (true, false, or a condition asked for each entity with `'$'` as it), and give each listed entity `flags`, named true/false conditions a UI can split a list by. See [Listing](/docs/reference/entities#listing).
- `'$'` is bound inside a plugin or custom call's arguments too, so a kind can list its entities with `{ 'cast/met': { character: '$' } }`.
- A guide page, [Organising a game](/docs/guide/organising): where content goes as a game grows, combining your files, prose files, tests per area and mods.
- [Content and packs](/docs/reference/loader#content-and-packs) on the loader's page: what your own content is, what a pack is, and how each merges, is saved and is upgraded.
- `loadGame` reports a scene, prose key, stat, entity, custom function, plugin entry or any other key that your content declares twice, so `ifloom check` fails on it and a game split into files can't lose one by accident. Give a file's content a `name` and the problem names both files.
- `npm create ifloom@latest my-game` (also `pnpm create ifloom`, `yarn create ifloom` and `bun create ifloom`), from the new `create-ifloom` package: a new game in the folder `my-game`, with the same `--template` and `--theme` as `ifloom new`, and the next steps written for the package manager you ran it with. With yarn 2 or later it also sets yarn to install into `node_modules`, which Vite needs.
- The packages are compiled JavaScript with type declarations and source maps, so a game installs them with npm, pnpm, yarn or bun, and any bundler uses them with no extra settings. Until they're on npm, `npm run pack` in the checkout packs them for a game beside it.
- `@ifloom/react/styles.min.css` and `@ifloom/react/themes/<preset>.min.css`: the React UI's stylesheet and its presets already built, for a game without Tailwind.
- An engine for any shape of game: a linear novel, a management game played a week at a time, or a life sim with a calendar, places and characters.
- A small core that keeps the turn, scenes and choices, stats, entities and who holds them, a kv store (keys with a true/false, number or text value), storylines, triggers, notices, inputs and saves.
- Plugins for the rest, each a package of its own: a calendar, places, a cast of characters, quests, a wardrobe, messages, feeds, devices, a ready-made phone, and debug commands that are left out of release builds.
- Content as data. Conditions and effects are plain objects, and your game's own logic plugs in by name, from its `rules`, with `{ 'game/name': args }`.
- `ifloom check`, which checks a game's content and lists any missing pictures, videos and audio files before anyone plays.
- Every choice is remembered, so a later scene can ask what the player chose.
- Stats you declare yourself, with optional levels, derived stats worked out from a formula, and stats that belong to kinds of entity.
- Seeded randomness. The same save on the same turn gives the same result, so undo can't re-roll and playtests repeat exactly.
- Weighted variants and storylets: scenes drawn at random from a set, each with a weight and its own conditions.
- Saves with undo and redo, a backlog, autosave, export and import, and storage in memory, localStorage or IndexedDB.
- Saves that survive game updates. Give your game a `version` and `migrations`, and older saves load into the new version.
- A profile that outlives saves, settings your game declares, and New Game+.
- Every line the player reads comes from a strings table, so a game or a translation can reword it.
- Mods: data-only files that players add at runtime, checked against the game and recorded in saves.
- The React UI, `@ifloom/react`, with `mountGame` to start a game in one line, a title screen, settings, load and credits pages, and four theme presets: paper, terminal, studio and storybook.

### Changed

- **Breaking (types only):** the interfaces a plugin augments are named as registries: the `Traits` interface is now `TraitRegistry`, and `View.plugins` is typed `ViewsIn`. A `declare module '@ifloom/engine'` block that adds to `interface Traits` adds to `interface TraitRegistry` instead. See [Typed calls, queries and views](/docs/reference/plugins#typed-calls-queries-and-views).
- **Breaking (types only):** `EntityRef` is `` `${string}:${string}` ``, a kind and an id, so a bare id where a reference is wanted fails to compile, and `Holder` is an `EntityRef`, `'player'` or `'you'`. What the engine hands back is typed `EntityRef`. The functions that read an entity (`entityName`, `entityOf`, `heldCount` and the rest) still take any string, as content writes them.
- **Breaking:** the places plugin's types are named for places, so they no longer shadow the browser's `Location`: the `places/location` trait's type is [`Place`](/docs/plugins/places#the-location-trait), what `location()` takes is `PlaceDef`, and the view's room is a [`PlaceView`](/docs/plugins/places#placeview). The trait id, the `location` kind and the `location()`, `locationRef()` and `locationOf()` helpers keep their names.
- **Breaking:** a place is an [entity](/docs/reference/entities) with the `places/location` trait, written in your content's `entities` with [`location({ ... })`](/docs/plugins/places#location), as a person is written with `person()`: `location({ id: 'cafe', name: 'The Corner Café', desc: 'Café', exits: ['high-street'], body: [{ text: 'place.cafe' }] })`. A place's old `tag` is its entity's `desc` and its `art` its `image`, which the checker now lists as a file to look for. The exits, body, actions and the rest are the trait's, so a mod changes a place with a `traits` row or replaces it as any entity. Any entity carrying the trait is a place, of any kind. `data.places.locations` is reported, and a pack written for an older schema is carried forward. The old reference helper `location('park')` is [`locationRef('park')`](/docs/plugins/places#helpers), `locationById` is [`locationOf`](/docs/plugins/places#helpers) and `locationsOf` gives references. The places view's `tag` and `art` are `desc` and `image` (a path through `artSrc`, or `null`), with the place's `ref` beside them, and the value `{{v:places/tag}}` is `{{v:places/desc}}`.
- **Breaking:** a vendor is an entity with the `shop/vendor` trait, written in `entities` with [`vendor({ ... })`](/docs/plugins/shop#vendor), its name the entity's. Any entity carrying the trait sells, so a person can keep a stall: `buy('character:ava', 'food:bun')`. `data.shop.vendors` is reported, and an older pack is carried forward. `vendorDefs` is [`vendorsOf`](/docs/plugins/shop#vendorsof-vendorof-and-vendorref), which gives references, and [`vendorOf`](/docs/plugins/shop#vendorsof-vendorof-and-vendorref) reads one.
- The checker reports a place or vendor content names that the game lacks as `unknown entity "location:moon"`, and one that names an entity without the trait as `"item:paper" has no places/location trait`. A place's and a vendor's own problems are at `trait places/location on location:cafe`.

- **Breaking:** a spoken line under a name, `Ava: "…"`, is a line under that label with no speaker: the engine no longer matches names against entities, and `You: "…"` is no longer the player's. Write `@ava:` and `@you:` (see [Speech](/docs/reference/prose#speech)). A pack written for schema 22 is rewritten when it loads: a line under exactly one entity's name gets that entity's id, `You:` (or the game's string `you`) becomes `@you:`, and a name nobody has, or two share, stays a labelled line.

- **Breaking:** the strings lookup is `stringOf(game, key, vars)` (was `say`), so `say` is only the flowing-scene builder for a spoken line. A plugin's refusals read `stringOf(game, 'loyalty/notFull')`. See [`stringOf`](/docs/reference/strings#stringof).

- **Breaking:** a minigame's numbers are its kv store, as `{ kv: 'score', of: 'minigame' }` already read them: `MinigameDef.kv` (was `vars`), and `kv` on the running `MinigameState` and on `view.minigame`. The checker says "key" for "variable". Old packs (schema 22) and saves (version 20) are carried forward.

- **Breaking:** a choice's `labels` entries name their words `label`, as an action's do: `{ when, label }` (was `key`). A pack of an older schema is rewritten when it loads. A choice's `effects` can be left out.

- **Breaking:** who a scene's speaker is comes from their entity, with no plugin to ask. A scene's `speaker` names an entity, by reference (`'character:ava'`) or a bare id (`'ava'` is `character:ava`, else the one entity with that id), and the view shows its name, picture and hints. A message's and a post's `from` work the same way, so any entity can send one. The speaker's picture is their entity's `image`: the `art/character/<id>.jpg` the cast used to guess is gone, so give each speaker an `image`.
- **Breaking:** `SpeakerView` has `ref` and `image` (was `portrait`), `view.scene.stageImage` is `view.scene.image`, and a hand-built scene's `portrait` is `image`.
- **Breaking:** the engine's beats are text, speech, pictures, video and sound. A letter, a note and a `> ` line are the React UI's inline pieces, `[[ui:mail|…]]`, `[[ui:prop|…|sticky]]` and `[[ui:mono|…]]`, and a picture's `rot` flag is the React UI's `tilt` block hint. A pack of an older schema is rewritten when it loads (schema 22). In your own prose, rewrite `[[mail]] … [[/mail]]`, `[[sticky]]`, `[[clip]]`, `[[diary]]`, `> ` lines and `|rot` the same way.
- The devices plugin's prose section is `{ type: 'prose', text, beats }`, and its React UI draws the beats. A message's and a post's `text` is the words of its beats.

- **Breaking:** an effect is told apart by its key, as a condition is, not by `kind`. The key says what it changes and its value is the target: `{ kind: 'stat', stat: 'coins', by: -2 }` is `{ stat: 'coins', by: -2 }`, `{ kind: 'kv', key: 'met', to: true }` is `{ kv: 'met', to: true }`, `{ kind: 'scene', to: null }` is `{ scene: null }`, and `{ kind: 'timer', timer: 'phone' }` is `{ timer: 'phone' }`. The rest read the same way: `{ entity, at, by }`, `{ create: 'photo', with: { name }, at }` (what was `of` and `entity`), `{ remove: 'staff:ana' }`, `{ each: 'staff', where, effects }` (or `each` a [`Select`](/docs/reference/entities#select)), `{ move: 'gift:scarf', to }`, `{ you: 'character:ava' }`, `{ scene: { from, otherwise } }`, `{ turn: true }` and `{ turn: { by: 2 } }`, `{ closeStoryline: 'baker', turns }`, `{ notify: 'Payday', text }`, `{ audio: 'music', to }`, `{ sound: 'bell' }`, `{ minigame: 'darts' }`, `{ roll: 'skim', dice, against }` and `{ panel: 'shop', with }`. A pack written for an older schema is rewritten when it loads, effects inside a plugin's `data` and an entity's traits included.
- **Breaking:** a call to a plugin's or the game's effect is always the short form, `{ 'calendar/pass': { by: 2 } }`. The long form `{ kind: 'custom', name, with }` is gone. Commands keep `type`, and `{ type: 'custom', name, with }` still sends a plugin's command. [`callOf`](/docs/reference/plugins#callof) reads a call's name and arguments, for code that looks through effects.
- **Breaking:** "kind" means only a kind of entity. A scene block, a prose span and a part of a line say what they are in `type` (`{ type: 'sound', track }`, `{ type: 'ui', name }`), and so do an input (`{ id: 'name', type: 'text' }`), a setting (`{ type: 'toggle' }`), a missing file the checker lists (`FileRef.type`) and a section of a device's app (`{ type: 'panel' }`). `FillKind` is `FillPart` and `fill(kinds)` is `fill(parts)`, the first argument of `argProblems` and `references.calls` is a `CallTable`, `mediaKind` is `mediaType`, and `ConditionKind` is `ConditionKey`, beside the new `EffectKey`. A pack's inputs and settings are rewritten when it loads.
- The checker reports an effect with two keys that each say what it does, as it does a condition, and an effect still written with `kind`.
- The content schema is 21. The statuses, devices, inventory, jobs, places, messages and cheats plugins' content is at version 21, rewriting the effects their content holds.
- **Breaking:** anything a mod could change is content now, so it goes in your content or a pack, never `loadGame`'s base: `actions`, `locks`, `resets`, `saveable`, `finished`, `carryOver`, `introScene`, `ui` and the starting `kv` (in place of `startPhase`), beside the `kinds`, `entities`, `traits`, `strings` and `data` content already took. Each is declared once across your content. A pack's action replaces one by id, its locks and `saveable` entries come after the ones before (a lock with an `id` replaces the one with that id), its `resets` and `ui` hints replace the content's key by key, and the rest replace the content's whole. The base holds only what the game is and its code: `id`, `title`, `version`, `plugins` and `rules`. Move the rest into a file of your content, such as the story file the game opens on. The loader reports any other key in the base.
- **Breaking:** `rules.locks` and `rules.resets` are the content keys `locks` and `resets`, and `game.locks` and `game.resets` on a loaded game.
- **Breaking:** `phone()` returns `{ plugins, content }`. Load `kit.content` beside your own content, `loadGame([kit.content, ...content], base)`, in place of spreading `kit.kinds` and `kit.data` into the base.
- **Breaking:** a plugin's `kinds` are in its `content`: `content: { kinds: [...] }`.
- **Breaking:** the game's own functions are in `rules`, and content calls them with `game` in front. `custom: { conditions, effects, values }` on the base folds into `rules`, and so do `migrations` and `saveName`. `{ custom: 'payRent' }` is `{ 'game/payRent': true }` (or with its arguments, `{ 'game/payRent': { weeks: 1 } }`), `{{v:rentDue}}` is `{{v:game/rentDue}}` and `{ value: 'ceiling' }` is `{ value: 'game/ceiling' }`. A plugin's call written `{ custom: 'quests/done', with }` is its short form, `{ 'quests/done': … }`. The type `Custom` is gone, and content and packs can't hold `custom` functions. `rules.onStat` is handed a context as well. Schema 18 carries old packs forward; the checker points at a call with no plugin in front.
- **Breaking:** `rules.commands`, which took over a built-in command by its type, is gone. Declare a command of the game's own in `rules.commands` by name and send `{ 'game/name': … }` instead.
- **Breaking:** no plugin can have the id `game`, which is the game's own code.
- **Breaking:** one kv vocabulary. The `kv` condition and effect read and write every kv store, with whose it is in `of`: an entity (`of: 'staff:ana'`), a storyline (`of: 'storyline:baker'`) or the running minigame (`of: 'minigame'`). `{ storylineKv: { storyline: 'baker', key: 'visits' }, gte: 3 }` is `{ kv: 'visits', of: 'storyline:baker', gte: 3 }`, and `{ minigameVar: 'score' }` is `{ kv: 'score', of: 'minigame' }`. The `storylineKv` and `minigameVar` conditions and effects are gone. The `kv` effect's `random: [min, max]` draws a whole number, seeded by the save, for any store. The `kv` condition's `is` takes a list too, `is: ['arrival', 'open']`, for any one of them.
- **Breaking:** the stretch of the game the player is in is the kv key `phase`, not a part of the engine. `{ phase: ['arrival'] }` is `{ kv: 'phase', is: ['arrival'] }`, `{ kind: 'phase', to: 'open' }` is `{ kv: 'phase', to: 'open' }`, and `startPhase: 'arrival'` is the content's starting kv, `kv: { phase: 'arrival' }`. `state.phase`, `view.phase` and the type `Phase` are gone. Save version 19 moves an old save's phase into `kv.phase`, and schema 19 carries old packs forward.
- **Breaking:** prose prints any kv store with `{{kv:key}}`, someone else's with `of`: `{{kv:visits of=storyline:baker}}`, `{{kv:mood of=character:ava}}`. `{{key}}` still prints the player's. `{{n:baker.visits}}` is gone.
- **Breaking:** a hand-built scene's context reads a storyline's key with `ctx.kv(key, 'storyline:baker')`; `ctx.storylineKv` is gone.
- **Breaking:** one kind of button. An [`ActionDef`](/docs/reference/actions#actiondef) has the fields a choice has: `label`, `when`, `blocked`, `cost`, `effects`, `command`, `once` and `ui`. Activities fold into actions: a button that ran an activity is one action with the activity's cost, reasons and effects, `{ id: 'coffee', label: 'Buy a coffee', cost: { stats: { coins: 3 } }, effects: [...] }`. An action with no label isn't a button and is done by its command. A button with a cost, effects or `once` sends `{ type: 'action', id }`, which runs its `command` first, then its cost and effects; one with only a command sends that command. A plugin's action is `{ type: 'action', id: 'places/coffee' }`, so a place's or an app's button can carry effects too. A lock that names a plugin, `deny: ['places/*']`, stops its actions as it stops its commands. `ActivityDef`, `ActivityCost` (now `ActionCost`), `activityBlocked` (now `actionBlocked`), `activityById` (now `actionById(state, game, id)`), the `activities` content key, the `activity` command and a lock's `'activity'` (now `'action'`) are gone. Schema 20 carries old packs forward, an activity as an action with no label, and `replay` reads an old log's `activity` commands as `action`.
- **Breaking:** one panel model. A scene's `panel` opens that panel for as long as the scene is open, `panel: { panel: 'prices', with: { stall: 'bread' } }`, and it is [`view.panel`](/docs/reference/panels#a-scenes-panel), with the scene's id in `scene`, as one the `panel` effect opens is. `view.scene.panel`, `view.scene.panelData`, a scene's `panelData`, `custom.panels`, `CustomPanel` and `customPanel` are gone: a panel that needs worked-out numbers reads them from the view or a value. The React UI draws a scene's panel in place of its choices, as before. A devices app's `{ panel }` section takes `with` too, and its view gives `with` in place of `data`. Schema 17 carries old packs forward: `panel: 'prices'` is `panel: { panel: 'prices' }`.
- **Breaking:** `state.seen` and `state.chosen` keep one record per scene or choice, `{ n, first, last }` (a [`Times`](/docs/reference/state#times)): how many times, and the turn of the first time and the last. They replace the counts and `seenOn`, `lastSeenOn`, `chosenOn` and `lastChosenOn`. `{ seen }`, `{ chose }` and `{ since }` read the same as before. Code that reads the state itself reads `state.seen['ava.hi']?.n` for the count. Save version 18 carries old saves forward.
- **Breaking:** a choice's `once: { per: 'turn' }` reads the choice's record in `chosen`, so it no longer writes a `turn:scene#choice` key into the kv store. An old save's caps for the turn it was made in still hold, under `once.key` too.
- **Breaking:** a save's `SaveMeta.player` is `SaveMeta.playerName`, so it can't be read as the `'player'` holder. A save written before reads with its name as `playerName`.
- **Breaking:** `upgradePack(pack, plugins)` takes the game's plugins, so each plugin's own steps run with the engine's. `loadGame` passes the base's plugins for you.
- **Breaking:** a mod is kept as its file wrote it, and `loadGame` upgrades it each time the game loads, with the game's plugins. So a mod a player installed keeps working when you update a plugin as well as the engine. `readMod` and the mod store's `add` only check that the engine can read its schema, and their `pack` is no longer upgraded. `unlockedPacks` works the same way.
- The engine's content migrations no longer know any plugin. What they did to a first-party plugin's content (the cast's characters, the shop's goods, the wardrobe's clothes, a place's transition, the statuses plugin's old names and the rest) is each plugin's own step now, and an old pack upgraded with those plugins comes out as it did before. The first-party plugins number their content versions by the engine's schema, so the shop's content is at 13 and the cast's at 16.
- **Breaking:** the React UI no longer draws any plugin by itself. Import each plugin's components and hooks from its `/react` subpath instead of `@ifloom/react` (`import { ShopCounter, useShop } from '@ifloom/plugin-shop/react'`), and list its `<plugin>Ui` in `plugins` for its panels, words and layout parts. The default layout places them at each `<Plugins at="…" />`; a copy of the old default layout in `src/layout.tsx` needs its plugin parts imported from their plugins, or replaced with `<Plugins at="…" />`.
- **Breaking:** codes are entered through the unlocks plugin's UI: list `unlocksUiWith({ problems, onChange })` from `@ifloom/plugin-unlocks/react` in `plugins`, in place of the `unlocks` prop. `useGame().unlocks` is gone.
- **Breaking:** the achievements page comes with `achievementsUi`. `PagesOptions.achievements` is gone: list `{ ...achievementsUi, pages: undefined }` to keep the achievements in a dialog.
- **Breaking:** the React UI's own `Inventory` lists `view.held` with no buttons. The inventory plugin's UI draws its `InventoryCard`, with the use and drop buttons, in its place.
- **Breaking:** `useClock()` gives only `when`. The calendar's pieces are `useCalendar()` from `@ifloom/plugin-calendar/react`.
- **Breaking:** the plugins' words, such as `buy` and `quests`, are in each plugin UI's table (`SHOP_WORDS`, `QUESTS_WORDS`), not `UI_STRINGS`. `ui.<key>` in a game's strings rewords them as before.
- The four presets style the kit's parts and the theme's tokens, never a plugin's own parts, so a plugin's UI looks right in each, yours included. Cards from different plugins now look alike in each preset: in `terminal`, every list heading is a `#` comment and every done entry is ticked.

- The `tick` command now runs the game's timers as well as a minigame's, whatever is open, and is refused with `Nothing is counting down.` (not `Nothing is being played.`) when nothing is. `startClock` from `@ifloom/browser` ticks while any timer runs, and the React UI runs it for the whole game rather than only while a minigame is on screen.
- **Breaking:** how a game looks and moves is the UI's, written as `ui` hints. A scene's or a place's `transition` is `ui.transition`, a block's `reveal` is `ui.reveal`, a stat's `display` is `ui.display`, and the cast's `hue` is the person's entity's `ui.hue`. A choice that used a `transition` effect gives itself `ui: { transition: { in, ms } }` instead. The game's `transitions: { default, names }` is `ui: { transition, transitionNames }`. Packs and mods written for an older schema are moved over for you (schema 16); your own content isn't, so TypeScript and `ifloom check` point at what to rewrite.
- **Breaking:** `[[reveal]]` is no longer prose markup. Put the paragraph that waits in a block of its own with `ui: { reveal: { delay } }`; `ifloom check` reports markup left in prose. A pack's prose is split into blocks for you where a scene's block uses it.
- **Breaking:** `SpeakerView`, the cast's `PersonView` and its `cast/person` query give `ui` in place of `hue`.
- Saves are version 17: a save no longer keeps `transition`. Older saves load as before.
- `ifloom playtest`'s numbers count only the kinds your game lists, so the places' `location` and the shop's `vendor` are no longer columns. A kind with `listed: false` of your own is left out too; give it `listed: true` or a condition to count it.
- **Breaking:** the cast's characters are entities. Write each one in your content's `entities` with [`person()`](/docs/plugins/cast#person), which puts their name, `desc` (once `role`) and `image` (once `portrait`) on the entity and their schedule, talk, call and the rest in the `cast/person` trait: `person({ id: 'sam', name: 'Sam', desc: 'Neighbour', home: 'park', talk: 'sam.hi' })`. `data.cast.characters` is no longer read, and `ifloom check` reports it. A pack or mod written for an older schema has its characters moved for it (schema 14). Anyone with the trait is a person, whatever their kind, and so is a thing made in play `like` one; conditions and commands take a reference (`'staff:ana'`) as well as an id.
- **Breaking:** the cast's `person('ava')`, which named a character's entity, is [`character('ava')`](/docs/plugins/cast#helpers); `person` now writes a character. `charactersOf` and `characterById` are [`peopleOf`](/docs/plugins/cast#helpers) and [`personOf`](/docs/plugins/cast#helpers), and the type `CharacterDef` is `PersonDef` (what `person()` takes) and `Person` (the trait).
- **Breaking:** the cast's `PersonView` and `cast/contacts` have `desc` in place of `role`, and the React UI's part `person-role` is `person-desc`. The devices plugin's contacts section shows the `desc`.
- The wardrobe keeps what each body wears: the player's, and each protagonist's the `you` effect switches to. Switching shows that one's clothes, and switching back the player's as they were. Old saves are carried over, to whoever the save was playing.
- The places view has `things`, what lies where the player is, and `usePlaces` in the React UI has `pickUp(ref)`.

- **Breaking:** items are things. The engine has no items of its own any more: what the player carries is [entities](/docs/reference/entities#holding-things) they hold, such as `{ id: 'sandwich', of: 'item', name: 'sandwich', at: 'player' }`, given with `give('item:sandwich')` and asked about with `{ entity: 'item:sandwich', at: 'you' }`. Using one is the [inventory plugin](/docs/plugins/inventory)'s `usable` trait and `inventory/use` command. A pack or mod written with items is upgraded as it loads (schema 13), and a save keeps what the player had, as counts held by the player (save version 16). Your own content isn't upgraded, so rewrite its items as things.
- **Breaking:** collections are things too. A note or a photo is an entity the player holds: declare it and `give` it, or make it in play with `create`, with its name, `desc` and `image`. The phone's kit returns `kinds` (its `photo` kind) instead of `collections`, and its Gallery lists the photos you hold. Old packs and saves are upgraded: a collection's entries become things of a kind named after it (the phone's `gallery` is `photo`), held by the player.
- **Breaking:** the strings `doesNothing` and `haveNone` are the inventory's, `inventory/doesNothing` and `inventory/haveNone`, and the wardrobe has its own `wardrobe/haveNone`. The inventory's and the wardrobe's lines name the thing as `{thing}`, not `{item}`.
- **Breaking:** the React UI's `Inventory` parts are `thing`, `thing-name`, `thing-count`, `thing-text` and `thing-drop`, and its words `ui.heldCount`, `ui.wearThing` and `ui.debugHeld`. A thing carries `data-thing`, and there's no `data-item`.
- Small Town's notes and photos are things you hold, read in the phone's Notes and Gallery apps, and its inventory lists only what you carry. Its coins read "1 coin".

- **Breaking:** the shop sells entities. A good is `{ entity: 'food:sandwich', price?, stock?, restock?, when? }` instead of `{ item, price }`, its price falls back to the thing's `sellable` trait, and `buy`, `sell`, `inStock` and the commands take the thing's reference: `buy('counter', 'food:sandwich')`. A good with no `stock` never runs out. A good with a `stock` is held by the vendor, now a unique entity `'vendor:<id>'`, which buying moves from and a restock tops up, so conditions and effects can read and change what it has. `GoodView` has `entity`, `desc` and `image` in place of `item`, and `VendorView` has `ref`. Saves carry their sold counts into the vendor's stock.
- **Breaking:** the wardrobe dresses you in entities. Instead of `data.wardrobe.clothes`, give each thing that can be worn `wearable(slot)`. A slot's `start`, `wear`, `wearing` and the view name things by reference (`'clothing:raincoat'`), `wardrobe/wearing` takes `entity` instead of `item`, and you can wear only what you hold. Saves carry worn item ids into references.

- **Breaking:** a save keeps only what play changed about an entity. A declared entity has no record in `state.entities` until something changes it, and its name, description and starting numbers are read from your content, so a fix to them reaches old saves. One created in play keeps the name it was given. Read values with [`statValue`](/docs/reference/stats#statvalue), [`entityKv`](/docs/reference/entities#entitykv) and [`entityName`](/docs/reference/entities#entityname) rather than from the state. Saves are version 15, and older ones drop what they copied from content when they load.
- **Breaking:** `entitiesOf(state, game, kind)` and `entityOf(state, game, ref)` take the game. `entitiesOf` lists the declared entities in content order, then the ones created in play. `entityOf` gives what play changed (`{}` for a declared entity nothing has changed), or `undefined` when it isn't in the game.
- **Breaking:** `view.entities` lists only what may be shown: kinds whose `listed` isn't false, and entities whose `listed` and `visible` hold. A plugin's kinds aren't listed unless the plugin says, so the cast's characters appear once the player has met them instead of from the first turn. Each `EntityView` gains `desc`, `image`, `tags` and `flags`, each `EntitiesView` gains `unique`, and an entry's `kv` includes its declared keys.
- A declared entity is in the game unless it was removed, in any save, so one an update or a mod adds needs no filling. A game that redeclares a plugin's kind keeps the fields it leaves out, such as `listed`.
- **Breaking:** your game's own files are now `Content`, not packs. A file in `src/world/` or `src/story/` exports `Content`, which has no `id`, `schema` or `patches`: write `export const cafe: Content = { scenes, prose }`. A pack is now only what comes from outside your code (a mod, unlocked supporter content or a JSON export), with an `id`, a `schema` and optional `patches`. Content is never upgraded, since it's built with the engine it runs on, so in a plain-JS game `ifloom check` reports any old names after an engine update.
- **Breaking:** `loadGame(content, base, { packs })` takes your content and the packs separately. Content merges first, in order, and a key it declares twice is a problem. Packs go over it in order and replace what they repeat, as before. Mods and unlocked content move from the first list to `packs`: `loadGame(content, base, { packs: [...unlocked, ...mods] })`. Content given an `id`, `schema` or `patches` still loads, with a problem for each.
- **Breaking:** `game.packs`, and so a save's `packs`, list only the packs' ids, not your own files. Renaming or splitting your files changes nothing a save records.
- A save now warns only about missing mods. `LoadedSave.missingPacks` lists packs whose id starts with `mod:`, so renaming or splitting a game's own files never shows players a warning, and the React UI's line says "mods".

The Letter has a file per chapter, and The Corner Café keeps its staff, menu, actions and triggers in `src/world/`. A copy made with `--template novel`, `cafe` or `town` starts this way too.

Each file exports `Content`, and the game's `AGENTS.md` says where new content goes.

(`{ has }` and the item and collection kinds are gone: things are entities, see above.)
- **Breaking:** a command that names one thing names it `id`, and one that sets a value takes `to`. `setting` and `input` take `to` instead of `value`. The plugins' commands follow: `places/go`, `cast/talk`, `cast/call`, `quests/track`, `quests/seen`, `jobs/apply`, `jobs/work`, `jobs/quit`, `wardrobe/wear`, `wardrobe/takeOff`, `devices/open`, `devices/close`, `feed/seen`, `messages/read` (for its thread), `debug/scene` and `debug/go` take `id`, and `debug/turn` takes `to`. The helpers (`go`, `talk`, `trackQuest` and the rest) write the new shapes.
- **Breaking:** the plugins' conditions and effects name their target by its noun: `achievements/earned` and `achievements/grant` take `achievement`, `effects/active`, `effects/apply` and `effects/remove` take `effect`, `cast/at` takes `character`, `feed/post` names the new post `post`, and `calendar/pass` takes `by`.
- **Breaking:** one shape for anything that can be refused: `blocked: { when, reason, hide? }[]`, refused while `when` holds, with `hide` to leave the button off the screen. An activity's and a job's `requires` (met while true) are `blocked` the other way round, a place's and an app's `locked` are `blocked`, and choices and actions gain `hide`. `Requirement` is `Blocked`, `need(reason, when)` returns a `blocked` entry that holds while `when` doesn't, and the places plugin's `onlyAt` returns one too.
- Old packs and mods are rewritten to all of the above as they load (schema 6), and `replay` reads an old command log's commands. Saves are unchanged.
- **Breaking:** a game's own custom effects run in order, like plugins' effects. Each is called in its turn with the state the effects before it left, so two in a row compose. Before, they were all worked out up front from the state before the list. Prices, guards and locks still see them worked out against the state on screen (`previewEffects`), and `buildEffects` now passes them on as `{ kind: 'custom', name, with }`, which the long form can also name.
- **Breaking:** custom conditions, effects, values and panels get a context, as plugins' functions do: `(state, args, { game, query, value, roll })`. A custom function can ask a plugin's query or read a plugin's value instead of reaching into `state.plugins`. Custom values take arguments, `(state, args, context)`, and panels take `(state, context)`. `customCondition`, `customEffect`, `customValue` and `customPanel` return the function ready to call.
- **Breaking:** a plugin call's short form always takes its arguments as an object, or `true` for none. `{ 'places/at': ['cafe'] }` is no longer read as `{ value: ['cafe'] }`; `ifloom check` reports it. The first-party calls name what they took: `places/at`, `places/within` and `places/move` take `location`, `cast/here` and `cast/met` take `character`, `calendar/period` takes `period`, `calendar/weekday` takes `day` and `calendar/pass` takes `by`. The helpers (`at`, `here`, `period`, `pass` and the rest) write the new shapes, and the `places/known`, `cast/person` and `cast/where` queries take `location` and `character`.
- **Breaking:** plugins' values take arguments as conditions do, `(state, args, context)`. The messages and feed plugins no longer make a value per channel or feed: `messages/unread-texts` is `messages/unread` with `{ channel: 'texts' }`, and `feed/unseen-social` is `feed/unseen` with `{ feed: 'social' }`. In prose, arguments follow the name: `{{v:messages/unread channel=texts}}`. A devices app's badge, a stat's `max` and an achievement's progress name a value as `{ value, with }`: the badge's `{ count }` is `{ value }`.
- Commands take the short form too: `{ 'places/go': { id: 'cafe' } }` works as an action's or a choice's `command`, and in `apply`, `whyNot`, `effectsOf` and the runner. The view still shows the long form. `CommandRef` is its type and `commandOf` reads one into the long form.
- `loadGame` reports a key a pack can't hold, such as `actions`, as `a pack has no "actions", so it was left out`, instead of dropping it without a word.
- **Breaking:** one naming rule for plugins' members and the game's rules. A hook runs at an event and returns the next state, and is named `on` and the event; anything else is a provider named by its noun. A plugin's `hooks: { turn, after }` are now `onTurn` and `onCommand`, beside its other members, and `profile: { onCommand }` is a `profile` function. A plugin's `migrations` steps get the game's `MigrationTools` as a second argument.
- **Breaking:** `rules.turn` is gone, folded into `rules.onTurn(state, context)`. `state.turn` is the turn beginning, `context.before` is the state the turn ended on (what `rules.turn` was asked about), and `context.apply(effects)` applies effects in order, each seeing the last, in either form, so a day's end needs no running totals. Write `turn: () => ({ effects })` as `onTurn: (state, { apply }) => apply(effects)`.
- **Breaking:** anything a mod could change is content now, not a plugin option. `devices()`, `messages()`, `feed()` and `wardrobe()` take no options: devices and apps go in a pack's `data.devices.devices` and `data.devices.apps`, channels in `data.messages.channels`, feeds in `data.feed.feeds`, and slots in `data.wardrobe.slots`, each slot with what the player starts wearing in it as `start`. A mod can add any of them. `phone()` returns the phone as `data` beside `plugins` and `collections`; pass it as the game's `data`. The places plugin's `arrive` option is a place's `arrive: { when?, effects }` in its content. Readers `devicesOf`, `appsOf`, `channelsOf`, `feedsOf` and `slotsOf` list them. A message, post, app or clothing naming one the game doesn't have is reported as `unknown channel`, `unknown feed`, `unknown device` or `unknown slot`.
- **Breaking:** every first-party helper writes the short form, `{ 'quests/done': { quest } }`, commands included (typed `CommandRef`), and every plugin factory declares what it returns. A view still gives its commands in the long form.
- Old packs and mods are rewritten to the above as they load (schema 7): the first-party calls' bare values are named, badges' `count` becomes `value` with its arguments, and value tokens in prose and strings take their arguments.
- **Breaking:** the profile's own namespaces have prefixes. The engine's `settings` and `finished` are `core:settings` and `core:finished`, and the React UI's `gate` is `ui:gate`. A plugin keeps its bare id, and the content checker refuses a plugin id of `core` or `ui`. A profile stored under the old names is moved the first time it's read.
- **Breaking:** `@ifloom/engine` has one entry point. Deep paths such as `@ifloom/engine/scene.ts` no longer resolve; import from `@ifloom/engine`.
- **Breaking:** `@ifloom/plugin-effects` is `@ifloom/plugin-statuses`, with the id `statuses`, so its names no longer read like the engine's effects. `effects()` is `statuses()`, `applyEffect`, `removeEffect` and `effectActive` are `applyStatus`, `removeStatus` and `statusActive`, `EffectDef` is `StatusDef`, `effectDefs` is `statusesOf`, and the rest follow. Its calls are `statuses/active`, `statuses/apply` and `statuses/remove`, taking `status` (commands still take `id`), its content is `data.statuses.statuses`, and its view is `view.plugins.statuses`. Old packs and mods are rewritten as they load (schema 8), and old saves load with the plugin's state moved (save version 13). The docs page moved to `/docs/plugins/statuses`, and the old address redirects.
- **Breaking:** the debug plugin's helpers are named after their commands, so they don't read like content: `setStat`, `setKv`, `setItem`, `jumpTo`, `setTime`, `setTurn` and `goTo` are `debugStat`, `debugKv`, `debugItem`, `debugScene`, `debugTime`, `debugTurn` and `debugGo`. The commands are unchanged.
- **Breaking:** places no longer have a `kind`. A place's `'street' | 'venue' | 'room'` meant nothing to the engine but a genre, so it's free `tags` now, which the places plugin passes through without reading. `LocationKind` is gone, and the places view's location and exits carry `tags`. Old packs and mods are rewritten as they load (schema 9), with each `kind` as a tag.
- **Breaking:** the React UI's built-in boxes are cards, so "panel" only ever means a game's own component in `panels`. `LocationPanel`, `PeoplePanel`, `WardrobePanel`, `DebugPanel` and `MinigamePanel` are `LocationCard`, `PeopleCard`, `WardrobeCard`, `DebugCard` and `MinigameCard`, in `components` overrides too. Their parts and classes are unchanged.
- **Breaking:** one separator rule for ids: `.` joins the parts of an id, `/` names a plugin, `#` is a choice in a scene, and `:` is a reference such as `character:ava`. A choice is now `scene#choice` everywhere, as its label already was: `{ chose: 'ch1.mat/open' }` is `{ chose: 'ch1.mat#open' }`, and `state.chosen` is keyed the same way. Old packs and mods are rewritten as they load (schema 10), and old saves load with their counts rekeyed (save version 14). The examples, templates and docs write prose sub-keys with a `.` (`place.cafe.ava`, not `place.cafe/ava`); your own keys with a `/` still work, but keep `/` for plugins. The docs explain the rule in [Ids and separators](/docs/reference/game#ids-and-separators).
- **Breaking:** a stat's hidden `bands` are levels the player isn't shown, so one condition reads both. `bands: [10, 20, 30]` is `levels: { at: [10, 20, 30], hidden: true }`, the `{ tier: 'charm', gte: 2 }` condition is `{ level: 'charm', gte: 2 }`, and `tier()` and `statBand` are gone: `levelAt(value, at)` and `statLevel` do both jobs. A hidden stat's view has no `level`. Old packs and mods are rewritten as they load (schema 11).
- **Breaking:** `saves.list()` lists saves that can't be read too, after the rest, as `{ slot, broken }` with the reason (`SaveListing` and `BrokenSave`), so a player can delete one instead of it hiding in storage. Tell them apart with `'broken' in entry`. The React UI's save menu and load page show them with a Delete button (`ui.brokenSave`), and `useSaves` gives them as `broken`.
- **Breaking:** anything that can fail in a way you should expect answers with one shape, `Result<T>`: `{ ok: true, value }` or `{ ok: false, reason }`, and never throws. `runner.apply`, `runner.save`, `runner.load`, `replay`, `loadState`, `readMod`, `upgradePack`, `saves.read`, `saves.importText` and `mods.add` return it, where they returned a value or a string. A runner with no `saves` answers `save` and `load` with `This game keeps no saves.` instead of throwing, a failed write with `The game could not be saved.`, and loading an empty slot with `Nothing is saved there.` (`noSaves`, `notSaved` and `emptySlot` in the strings table). The engine's `apply` keeps the state on both sides, and its refusal is `reason` instead of `refused`. `Runner`, `Saves` and `Mods` are declared interfaces.
- **Breaking:** settings live in the runner. `runner.settings()` gives every setting's value at once, play and ui, and `runner.setSetting(id, to)` changes either kind: a play setting as the `setting` command, kept for the next game, and a ui setting in the profile. `setUiSetting` is gone, and so is the `notAUiSetting` string (`noProfile` is new). React's `useSetting`, the settings page and `@ifloom/audio` read settings from the runner, so the settings page changes a play setting in the game in play from the title screen too.
- **Breaking:** `browserRunner` and `mountGame` are async and read the player's profile before they start, so a new game has their stored play settings and a ui setting such as a volume is right from the first frame. `await browserRunner(game)`; `mountGame` can still be called without waiting. `browserRunner`'s `settings` option is gone.
- **Breaking:** plugins' views share their shapes. A places exit is a button like any other (`ExitView` is a `RenderedChoice` with the place's `tag`, `tags` and `art`), so its name is `label`, not `name`, and it gains a `price` when a plugin gives one. A message's `replies` are `RenderedChoice`s. A feed counts news as `unread` in the view, as messages do, not `unseen`. A vendor's view has only `closed`, null while it's open: `open` is gone. A cast `PersonView`'s `portrait` is typed `string | null`, as every plugin's portrait is.
- `definePlugin<State, View>` keeps the view's type, and a defined plugin's `viewIn(view)` reads its slice of a view typed: `quests().viewIn(runner.view())?.active`. The first-party plugins declare theirs. The React UI's plugin cards take the plugins' exported view types with `import type`, so they can't drift from the plugins; the plugins are optional peers of `@ifloom/react`, and none is bundled into it.
- `storylines` and `activities` are optional on `Game`, like its other lists, so a game built by hand without any can leave them out. Code that reads them should allow for `undefined`.
- **Breaking:** the Vite preset `@ifloom/cli/vite` knows no UI framework. It no longer adds React's and Tailwind's Vite plugins for a game that depends on `@ifloom/react`, and its `react` and `tailwind` options are gone; it builds one HTML file with relative paths, and a game adds its framework's plugin in `vite.plugins`, as Vue and Svelte games already did. A React UI game adds `react()` and `tailwindcss()` there and lists `@vitejs/plugin-react`, `@tailwindcss/vite` and `tailwindcss` in its `devDependencies`, as the `react` template and the examples do (see [The Vite preset](/docs/cli#the-vite-preset)). `@ifloom/cli` no longer depends on them.
- **Breaking:** `ifloom new`'s default template, `blank`, is called `react`, after the UI it draws with, beside `vanilla`, `vue` and `svelte`. `--template blank` is now `--template react`, or leave it out.
- Every `@ifloom` package names another it uses as a peer dependency with a caret range, `^0.0.0`, instead of the exact `0.0.0`, so a game has one copy of each. `@ifloom/react` takes `@ifloom/audio`, `@ifloom/browser`, `tailwindcss` and React's types as peer dependencies rather than bundling its own, which npm 7 and later installs for you. New games list `^0.0.0` too, and the templates have a `typecheck` script with TypeScript pinned.
- The docs have a Recipes section for the pages that show how to build one piece of a game: the title screen and settings, a HUD, UI for plugins, a minigame, transitions, and actions and tooltips in the text. The guide keeps the tutorials. The audio player and the browser helpers moved from the engine's reference to a Browser section, at `/docs/browser/audio-player` and `/docs/browser`. The old addresses redirect.
- **Breaking:** the feed plugin's value `feed/unseen` is `feed/unread`, to match its view and the messages plugin: `{{v:feed/unread feed=social}}`, and a badge's `{ value: 'feed/unread', with: { feed } }`. Old packs and mods are rewritten as they load (schema 12); a custom function that reads the value by name needs the new name.
- **Breaking:** `GameShell`'s and `mountGame`'s `layout` is a component, your `src/layout.tsx`, instead of lists of part names. With none, you get `DefaultLayout`. The `Frame` override is gone, since the layout draws the page itself, and so is `GameShell`'s `className`; give `Game` a `className` instead.
- **Breaking:** the React UI's page is fluid. With a side column it fills the window, the side column `--width-sidebar` wide and the story the rest; `--width-page` is gone. Exits, the room's actions and the people here are at the bottom of the story, and the stats, quests, people met, inventory and wardrobe are sections in the side column.
- **Breaking:** the React UI's main region is `story`, not `stage`: its `data-part`, its key in `classes`, and the presets' styles. `stage` now only means the layered picture.
- **Breaking:** `PeopleCard` is `PeopleHere`, `Actions` is `RoomActions`, and `LocationCard` draws the place without its exits, which are `Exits`. `Title` no longer has the clock under it; `Clock` goes where you put it.

### Removed

- The achievements plugin's `ProgressValue` type and `progressValue` function: a progress value is an [`Amount`](/docs/reference/amounts), read with `amountOf`.
- **Breaking:** a plugin's `entities` provider. A plugin brings entities in its [`content`](/docs/reference/plugins#kinds-and-entities), and the places and shop plugins read theirs from their traits.
- **Breaking:** the `mono`, `mail` and `prop` beats, an image beat's `rotate`, `MailHeader`, `PropFace` and the React UI's `ui.mailHeader` word.
- **Breaking:** a plugin's `speaker` provider, `pluginSpeaker` and the cast's `cast/person` query. A scene's speaker is its entity.
- **Breaking:** `renderScene`, `defaultRuntime`, `SceneRuntime`, `Prose` and `drawVariant` aren't exported. A plugin draws blocks with `context.beats`.

- **Breaking:** from `@ifloom/react`: every plugin's component, hook and type (`ShopCounter`, `QuestLog`, `DebugCard`, `useShop` and the rest, now in each plugin's `/react`), `UnlocksOption`, and its optional peer dependencies on the plugins.

- The browser editor at `/editor`, until the content API settles. Its old address goes to the homepage.
- **Breaking:** the engine's transitions: the `transition` effect, `state.transition`, `view.transition`, `game.transitions`, `TRANSITIONS`, `Transition`, `TransitionName`, `TransitionView` and `Reveal` (the React UI exports its own), the `reveal` beat, and `StatDisplay` and `StatView.display`. Scenes lose `frame` and the view's `scene.frame`, which nothing drew differently; a UI that wants a conversation layout can look at `scene.speaker`.
- **Breaking:** `@ifloom/browser`'s `revealGroups`, `lastReveal`, `RevealBeat` and `RevealGroup`. The React UI has `revealGroups` and `lastReveal` for its own hints, and the [Transitions recipe](/docs/recipes/transitions#draw-them-yourself) shows another UI how to time reveals. `startRevealSkip` stays.
- The cast's `data.cast.characters`, `charactersOf`, `characterById` and `CharacterDef`, and the plugin's own entities provider: characters are entities your content writes (see Changed).

- **Breaking:** core items: `ItemDef`, `itemById`, `itemStart`, the `items` key of a game, content and pack, the `{ item }` condition, the `item` effect, the `use` command, `view.pack`, `state.items`, `CarryOver.items`, the `items` kind of `MigrationTools.fill`, and the debug plugin's `debug/item` and `debugItem`. Use things the player holds and the inventory plugin.
- **Breaking:** collections: `CollectionDef`, `CollectionItem`, `CollectionEntry`, `CollectionView`, `collect`, `collected`, `collectionById`, `discard`, the `collections` key, the `{ collection }` condition, the `collect` and `discard` effects, `view.collections`, `state.collections`, the devices plugin's `{ collection }` section and `PhoneKit.collections`. Use things the player holds.
- **Breaking:** the `entities` kind of `MigrationTools.fill`, and the filling of declared entities into old saves: they're there without it.
- **Breaking:** a pack's `overrides` field, since every pack replaces what it repeats and your own content declares each key once. An old JSON pack or mod that sets it still loads, and the field is ignored.
- The React UI's layout lists: the `Layout`, `Part` and `PartName` types, `DEFAULT_LAYOUT`, `READING_LAYOUT`, `Parts`, `Frame` and `FrameProps`, and `Sidebar`'s `parts`. Write the page as a layout component instead.
- `validatePack` and `referenced`. Use `checkGame` to check a game's content.
- `migrate`, `migratePlugins`, `migrateGame`, `deserialize`, `serialize` and `hydrate`. Use `loadState` to load a save or any other state from outside.
- The built-in "Wait a while" action. A game declares the actions it offers everywhere in `Game.actions`.

### Fixed

- The docs said saves were at version 16 while the engine wrote 17. They're at 18 now, and the docs say so.
- The React UI's `LocationCard` leaves a gap between the place's line and the things lying there.
- A stat drawn or written on a thing made `like` another is kept when a save loads, even when it equals the stat's `start`, so it no longer reads the other's value instead.
- The React UI's debug card sends the place, scene and turn forms with the arguments the debug plugin reads, so they work.
- A name with a prose token, such as a character called `'{{partnerName}}'`, is filled in `view.entities` too, not only in the cast plugin's own view.
- In the React UI with `keys` on, Escape is left to the page again when there's no menu on screen, instead of being swallowed. `startKeys`'s `escape` can return `false` to let the key through the same way.
- On a phone, the React UI no longer leaves a gap between the side column and the scene. The page's rows now start at the top instead of stretching to fill the window.
- The terminal preset's status line of notices no longer covers the top of the page. It's now the first row of the page and pushes everything else down, so the scene title, the notice strip and a minigame stay in view. On wide screens it sticks to the top as you scroll.
- Every dialog in the React UI (the menu's, saves, backlog, mods, codes, a device, the notice strip's, the shop, cheats and achievements) is drawn the same way: in the preset's body font and colours, with a gap at the sides on a phone, and no taller than the window, scrolling inside. Tooltips take the preset's font too.
- Checkboxes, radio buttons and sliders in the React UI take the preset's colour instead of the browser's blue, and the terminal preset tells the browser it's dark, so native controls draw dark.
- While a dialog is open, the React UI's notices wait behind it, so on a phone they no longer show under the bottom of a long dialog.
- A job whose shift is done for the day says `You’ve done today’s shift.` instead of `Not a time for a shift.` or `No shift today.`, because the shift itself moved the clock on.
- The cast plugin fills prose tokens in a character's `name` and `fullName` wherever it shows them (their card, a scene's speaker, `cast/person`, `cast/contacts` and its refusals), so `name: '{{friendName}}'` shows the name the player typed into an input.
